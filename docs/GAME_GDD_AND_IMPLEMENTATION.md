# 《空间站重启》游戏 GDD 与 Unity 实现方案

版本：1.0 · 日期：2026-09-15 · 状态：可交付实现 Agent

配套文档：[履带机器人建模与动画指南](./ROBOT_BLENDER_GUIDE.md)。本文件负责游戏规则、Unity 系统、编辑器及验收；配套文件负责角色资产。两份文档共享 `robot-asset-v1` 交付约定。

## 0. 给实现 Agent 的任务说明

在本仓库建立并实现一个 Unity 3D 推箱子小游戏。使用白模完成游戏闭环、供电机制、低摩擦轨道、双视角、Unity 内关卡编辑器和三张正式关卡。机器人后续由 Blender 资产替换。必须先建立关卡数据与编辑器的制作链，再通过它制作关卡。

### 0.1 已确认的产品边界

| 项目 | 本版决定 |
|---|---|
| 开发目标 | 一周内交付可玩的版本；完整关卡目标 3 张，最低交付 2 张 |
| 平台 | Windows 桌面、键盘鼠标；这是本方案的默认交付平台 |
| 移动 | 机器人和箱子都按正方形网格、四方向移动，表现层平滑插值 |
| 默认视角 | 第三人称冒险游戏式跟随镜头，鼠标可自由环绕机器人 |
| 第二视角 | 随时切换至固定朝向的正交俯视镜头，保持同一局面 |
| 核心机制 | 能源箱、供电插槽、受电门；低摩擦轨道也必须完整实现 |
| 轨道使用 | 正式三关先不用；编辑器可放置，专门测试关和自动测试覆盖 |
| 编辑器 | Unity 内的开发者工具；不要求在发布后的游戏中编辑关卡 |
| 角色 | Blender 制作的简单履带机器人；仅 Idle、Move、Push 三种机械动画 |
| 表情 | 推不动与通关等使用角色上方表情气泡，由 Unity 实现 |
| 美术 | 初期全部白模；造型、色彩和灯光遵循简约科幻方向 |
| 后续关卡 | 都使用本文定义的编辑器、数据格式、校验、试玩和发布流程 |

### 0.2 工作起点与执行约束

- 规划时仓库只有 README、LICENSE 和 Git 配置文件，尚未创建 Unity 工程。
- 用户指定引擎版本为 **Unity `2022.3.51f1`**，本机也已安装。工程必须使用这个精确版本创建、测试和构建；执行环境缺失时先补齐该版本，不能自行升级引擎。
- 在仓库根创建工程，提交 `Assets`、`Packages`、`ProjectSettings` 及对应 `.meta`。保留已有文件和用户修改。
- 使用 URP 14.0.x，具体补丁版本采用 `2022.3.51f1` 对应的 URP 模板/Package Manager 解析结果；使用 Input System 的兼容稳定版本，并锁定到 manifest/lock 文件。
- 相机使用 Cinemachine 2.10.x，优先采用官方为 Unity 2022.3 列出的 2.10.7；使用 `CinemachineVirtualCamera`、`Cinemachine3rdPersonFollow` 和 `CinemachineBrain`，不混用 3.x 类型名。实际包解析结果必须记录并验证编译。
- 先用默认材质与几何体完成交付；不得让正式角色或外部素材下载成为功能开发的前置条件。
- 实现 Agent 每完成一个可验收阶段，运行相关检查、审查 diff、只暂存本阶段文件并提交。未经用户明确要求，不 push、不创建 PR、不发布。
- 完成本方案时必须交付可操作的 Unity 工程、Windows 构建、关卡数据、测试结果与操作说明；仅生成 C# 文件或场景截图不能作为完成。

### 0.3 范围控制

本版不安排战斗、跳跃、自由物理推箱、多层楼板、箱子堆叠、传送、拉箱、联机、玩家社区、运行时关卡编辑器、剧情配音、自动生成关卡、通用电路模拟和自动求最优解。撤销、双视角、编辑器和两个机制属于核心交付，不能被额外视觉工作挤掉。

## 1. 游戏定位与体验

### 1.1 一句话概念

玩家控制一台履带维修机器人，把能源箱送入空间站的供电插槽，借助临时供电打开道路，重新分配有限能源，最终点亮各区域的核心设施。

### 1.2 体验支柱

1. **操作可预测**：一条方向指令对应一次明确的网格动作；失败不改变谜题局面。
2. **能源可以挪用**：插槽既可能是最终目标，也可能是临时开路工具。
3. **观察方便**：第三人称提供空间感，俯视方便规划；切换镜头不会重置局面。
4. **试错轻松**：一次撤销回退整次推动及其引起的全部滑行、供电变化。
5. **制作过程可复用**：正式关卡、测试关与后续关卡使用同一编辑器和运行时。

### 1.3 游戏循环与完整流程

主菜单 → 关卡选择 → 关卡标题/一句目标 → 观察和推动 → 所有目标插槽通电 → 简短反馈 → 下一关/重玩/选关。

- 主菜单：开始、关卡选择、设置、退出。
- 设置仅需要主音量、鼠标灵敏度、反转垂直镜头；即时生效并保存。
- HUD：关卡名、已通电目标数/总数、移动次数、推动次数、视角切换/撤销/重开提示。
- 结算：关卡完成文案、移动/推动统计、下一关、重玩、选关；最后一关显示“空间站已重启”。
- 首次试玩的设计目标：L01 约 1–3 分钟，L02 约 3–6 分钟，L03 约 5–8 分钟。时间是待试玩调整的目标，不是已经测出的结果。
- 通关不要求走进额外出口；全部目标插槽稳定通电即完成。

## 2. 统一术语、坐标与空间约定

| 名称 | 定义 |
|---|---|
| Cell | 一个整数坐标 `(x,z)` 的棋盘格 |
| Terrain | 格子的基础类型：Void、Floor、Wall、LowFriction |
| EnergyCrate | 能被机器人推动一格并可能继续滑行的能源箱 |
| PowerSocket | 箱子占据时通电的插槽；玩家踩上去不供电 |
| GoalSocket | `isGoal=true` 的 PowerSocket，参与通关条件 |
| UtilitySocket | `isGoal=false` 的 PowerSocket，只作为机关电源 |
| PowerGate | 根据关联插槽的供电状态打开的门，占据一格 |
| MoveCommand | 一个世界方向 N/E/S/W 的完整逻辑操作 |
| Microstep | 一次命令中的初始位移或一次额外箱子滑行 |
| SettledState | 整条命令及全部滑行解析完后的稳定局面 |
| LevelDefinition | 关卡设计数据，保存地形、初始摆放、连接、文案 |
| GameState | 当前玩家/箱子位置及计数；不覆盖关卡初始数据 |

空间规范：

- 一个格子边长 `1.0 m`，地板顶面为 Unity 世界 `Y=0`。
- `(x,z)` 对应世界中心 `(x,0,z)`；格子边界为中心 ±0.5 m。
- `N=(0,+1)`、`E=(+1,0)`、`S=(0,-1)`、`W=(-1,0)`。
- 地图宽高包含边界；坐标从左下角 `(0,0)` 开始。
- 文本图和 `terrainRows` 从最北一行写到最南一行：第 r 行对应 `z=height-1-r`。
- 玩家和箱子的逻辑位置使用整数格坐标；Transform、碰撞体和动画不能反向决定占格。
- 地板固定单一高度；装饰可以有高度，但不形成第二层可行走区域。
- 箱子尺寸 `0.80 × 0.80 × 0.80 m`，根节点在底面中心，视觉中心 Y=0.40。
- 机器人静止包围盒约 `宽0.70 × 深0.68 × 高0.80 m`，详细接触尺寸见第 9 节。

## 3. 操作与双视角

### 3.1 默认输入

| 输入 | 行为 |
|---|---|
| W/A/S/D | 镜头相对的四方向网格移动；面对箱子时尝试推动 |
| 方向键 | 固定世界方向，↑=N、→=E、↓=S、←=W，适合精确操作 |
| 鼠标移动 | 第三人称模式下环绕观察；不改变机器人格坐标 |
| 鼠标滚轮 | 第三人称调整距离；俯视调整正交缩放 |
| V | 切换第三人称/俯视 |
| Z | 撤销最近一次成功命令 |
| R | 重开本关，清空本轮计数和撤销栈 |
| Esc | 暂停/返回；暂停时释放鼠标 |

- 游戏操作区锁定鼠标，暂停、主菜单、结算释放鼠标。编辑器 UI 不接收游戏移动输入。
- 同时按两个移动方向不形成斜走；以最近按下的有效方向为准。
- 按下立即尝试一格；持续按住先等待 0.25 s，再在上一动作完成后持续步进。不积压多条过期方向命令。
- 新按键最多缓存一个待执行方向；无效推动不增加计数，失败表情有 0.5 s 冷却。
- 重开、撤销、切关时清空输入缓存和长按状态，需再次按键才开始新动作。

### 3.2 第三人称方向映射

1. 使用镜头绕世界 Y 轴的轨道 yaw，而不是机器人朝向，确定当前相机前方。
2. 将 yaw 量化成最近的 N/E/S/W；W 对应该方向，S 相反，A/D 为左右各转 90°。
3. 扇区切换使用 8° 滞回：从当前扇区中心偏离超过 53°才切到相邻扇区，减少 45°边界抖动。
4. 一个按住的移动键在按下时锁定世界方向，直到松开；环绕观察不会使同一次长按突然转弯。
5. HUD 显示小型北向标记；方向键始终按世界方向解释。
6. V 切换时清掉尚未开始的移动输入；正在执行的命令继续，新模式需重新按下移动键。

### 3.3 镜头规格

**第三人称**：透视，FOV 初值 55°；围绕逻辑玩家跟随位置上方 0.55 m 的独立目标旋转，默认距离 3.2 m、可调 2.0–5.0 m，俯角初值 25°、限制 10–65°。鼠标水平可环绕 360°。角色转身不能强制把相机转到背后；提供进入关卡时的默认背后方向即可。

目标对象跟随玩家表现位置的平移，但不能继承头部摆动、机身前倾或推板动作。可用 Cinemachine Third Person Follow 加独立旋转目标处理环绕和避障；不要直接跟随会随移动旋转的模型节点。

**俯视**：正交、固定世界北方在屏幕上方。相机看向 `-Y`，屏幕上方为 `+Z`。默认居中棋盘并完整显示地图；初始 `orthographicSize=max(height/2+1,(width/2+1)/aspect)`。滚轮可缩放，缩小视野时以玩家为跟随中心，并将中心限制在地图范围内。

**切换**：V 在移动、推箱和滑行途中都能使用，立即开始镜头切换。采用约 0.25 s 的位置/旋转过渡；透视/正交投影在过渡末明确切换。不能依赖切换镜头重新载入关卡。正在进行的逻辑动作不改变方向或终点。

**遮挡**：第三人称相机避开墙壁；机器人、箱子、气泡不作为镜头碰撞障碍。近距离必要时淡出遮挡模型。俯视隐藏上层墙体、门顶和天花，保留墙体基座与门状态标记；这些隐藏只影响 Renderer，不能改变通行性。正式关卡至少要在窄门、贴墙、转角和推动过程中检查两种视角。

## 4. 游戏规则：唯一判定依据

以下规则必须同时用于正式游玩、编辑器试玩、测试和参考解法回放。不得为某一张关卡写特例。

### 4.1 基础移动和箱子

- 一条命令移动玩家一格；成功推动时，玩家进入箱子的旧格，箱子先前进一格。
- Void、Wall、边界外不可进入。封闭门不可进入。只能同时推动一个箱子。
- 两箱相邻时不能连推，不能拉箱、斜推、抬箱、堆叠或掉出地图。
- 如果玩家前方被阻挡，或箱子第一目标格不合法，整个命令失败，局面和计数不变。
- 失败时机器人可以在表现层朝向输入方向，并显示表情；这不是一次逻辑移动。
- 普通成功移动：移动数 +1。成功推动：移动数 +1、推动数 +1。额外滑行不增加任何计数。
- 一次动作的所有逻辑变化先计算完成，再交给表现层播放；表现层播放时不接受第二条逻辑动作。

### 4.2 供电插槽

- 每个插槽占一个普通 Floor 格；能源箱位于该格时通电，移开后断电。
- 所有能源箱等价；首版不做颜色匹配、容量或耗电。
- 目标插槽和辅助插槽都可以为门供电。目标插槽通电后仍允许移走箱子。
- `isGoal=true` 的插槽全部通电才算完成；至少要有一个目标插槽。
- 不要求所有辅助插槽同时通电；可以有多于目标插槽数量的箱子。
- 基础校验要求箱子数不少于目标插槽数；插槽总数可以大于箱子数，这是挪用能源谜题的基础。
- 本版插槽只放在 Floor 上，不能与 LowFriction 或门重叠。

### 4.3 受电门

- 一个门关联 1 个或多个插槽 ID，编辑器支持 `Any`（任一通电）和 `All`（全部通电），默认 Any。
- 一个插槽可以控制多个门；空连接和失效引用是校验错误。
- 门的电源状态仅由关联插槽计算，门不会向其他设备输出电源。
- 定义：`powered = Any/All(来源插槽通电)`。
- 定义：`effectiveOpen = powered || 门格被玩家或箱子占据`。
- 断电且无人占据时立即逻辑关闭；门格内有人或箱子时保持打开，直到格子腾空，避免夹住物体。
- 通行检查使用本次 Microstep 开始时的 effectiveOpen，先完成该步全部占格交换，再重算电源和门。
- 因此，箱子占据断电门时，玩家仍可把它推出门，同时进入它的旧门格；门继续保持打开，直到玩家也离开。这个行为属于明确规则。
- 门开合动画不延迟逻辑判定，不得用 Animator 状态或物理触发器判断是否通电。
- 门初始若被箱子占据，其 effectiveOpen=true；玩家初始生成点不能设在门上，以减少不易理解的开局。
- 门朝向只用于造型，不增加单向通行规则。

### 4.4 低摩擦轨道

低摩擦轨道是 `LowFriction` 地形，视觉可做成带方向纹理的光滑运输板；首版沿本次推动方向滑行，纹理方向不影响逻辑。

1. 只有箱子受低摩擦影响，履带机器人仍然一格一格走。
2. 箱子完成第一格推动后，如果所在格是 LowFriction，就继续尝试沿原方向前进一格。
3. 只要当前格仍是 LowFriction 且下一格合法，就继续；进入普通 Floor、插槽或打开的门格后停止。
4. 如果下一格是墙、Void、边界外、关闭门、其他箱子或玩家，停在当前格。
5. 受阻后没有连锁推箱、反弹、转向或延迟滑行；以后必须再次收到推动命令才会移动。
6. 玩家只进入原箱子格，不跟随箱子滑行。
7. 插槽和门都不能叠加在 LowFriction 上；停在插槽时立即按占格计算供电。
8. 如果箱子从插槽被推上轨道，第一格交换后就断电；后续滑行遇到该电源控制的关闭门，必须停住。
9. 一次推动加整段滑行是一条命令、一次撤销。滑行必须有限；循环最多经过当前方向上的地图跨度，超出即视为实现错误。

### 4.5 解析顺序

```text
TryResolve(definition, settledState, direction)
  1. 用当前占格重算电源和门的 effectiveOpen。
  2. 检查玩家下一格。
  3. 如果有箱子，检查箱子第一目标格；不合法则返回 Rejected。
  4. 在状态副本中原子更新玩家/箱子位置，记录第一条 Microstep。
  5. 重算供电和门，把变化附在该 Microstep 上。
  6. 若被推箱子当前在 LowFriction，逐格解析后续滑行；每格重复占格和供电更新。
  7. 更新一次移动/推动计数，仅在最终稳定局面判定完成。
  8. 返回完整的新状态及有序表现事件；原始状态保持不变。
```

阶段 1/3 的通行检查都基于各自 Microstep 开始的状态；如果门在同一步结束才关闭，不能追溯否决已合法完成的那一步。

### 4.6 撤销、重开、暂停与完成

- History 记录每条成功命令之前的玩家位置、带稳定 ID 的箱子位置、移动/推动数和恢复展示需要的朝向。
- 供电和门状态由恢复后的占格重新计算，不另存容易失配的副本。
- Z 在动作中也有效：取消表现任务和输入队列，回到这条命令之前的完整快照，机器人动画归位。
- R 在动作中也有效：取消所有表现任务，回到 LevelDefinition 的初始状态，不改变当前视角模式。
- 暂停冻结移动、动画、滑行和计时；恢复继续同一动作。UI 操作不进入 History。
- 镜头切换、环绕、失败输入、表情和音效都不进入 History。
- 完成逻辑只在最终稳定状态计算；完成 UI 在对应表现事件全部结束后出现，避免滑行中间短暂满足目标就结算。
- 结算界面允许 Z 回退继续解题；已解锁的下一关不重新锁定。关卡选择返回、切关和重新进入则开新局。
- 通关记录按关卡 ID 保存；最佳成绩按“推动数优先、移动数次之”保存同一局的成绩对，不分别拼接两局数据。不要求计算最优解或星级。

## 5. 正式关卡方案与可回放布局

### 5.1 配方格式

下面是策划配方，不是第二种运行时关卡系统。实现 Agent 必须用编辑器的配方导入/绘制命令生成工作文档，再经编辑器 Save 保存为统一 JSON。正式游玩读取保存出的 JSON，不能直接读取本 Markdown 或在 C# 中硬编码地图。

- `#`=Wall，`.`=Floor，`P`=玩家，`C`=能源箱，`D`=门。
- `a/b/c`=目标插槽，`s/t`=辅助插槽，`~`=LowFriction。
- 所有实体符号的基础地形都是 Floor；位置、连接以每关下方表格为准。
- 每个字母命令是一格世界方向：N/E/S/W。解法字符串与相机无关。
- 下列三关参考解法在编写文档时已用独立 Python 网格模拟器回放验证。L01/L02 使用广度搜索得到，L03 使用分阶段搜索；只证明该规则下可解，不代表 Unity 实现已测试、难度已验证或推动数最优。

## 6. 从第一天建立关卡编辑器

### 6.1 窗口与工具

入口：`Tools > Sokoban > Level Editor`。使用 UI Toolkit EditorWindow，配合 SceneView 网格交互。

| 区域 | 必需功能 |
|---|---|
| 顶栏 | 新建、打开、保存、另存为、校验、试玩、关卡目录 |
| 左侧画笔 | Floor、Wall、Void、LowFriction、玩家、箱子、辅助插槽、目标插槽、门、选择、擦除 |
| 中央 SceneView | 网格、坐标、落点预览、选中轮廓、拖刷、机关连线 |
| 右侧属性 | ID、格坐标、朝向、isGoal、Any/All、来源插槽列表、提示/完成文案 |
| 底栏 | 当前尺寸、未保存状态、错误/警告列表、点击定位问题格 |

基本交互：左键放置/选取，拖拽连续刷地形；右键擦除当前图层；Q/E 旋转门、玩家和装饰朝向；Ctrl+Z/Ctrl+Y 撤销/重做；Ctrl+S 保存；中键/Alt 操作保留 SceneView 导航习惯，避免抢占导航输入。

完整性要求：

- 支持 5–32 格的宽高；默认新图 9×9。新图可一键建立外围墙。
- 地形层、插槽/门层、动态实体层分别处理，擦除某层不会意外删除其他层。
- 涂 Wall/Void 时若该格有实体，预览说明会删除该格上的实体；一次刷操作及相关删除属于同一撤销组。
- 删除插槽时，同时删除门中的对应引用；变成空连接的门显示错误，直到修复。
- 缩图前显示将裁掉的元素数，确认后在同一撤销组处理越界实体和引用。扩图新增区域为 Void。
- 一个拖刷手势是一条编辑撤销；单次属性编辑是一条撤销；不能每帧刷出重复对象。
- 改变棋盘时使已记录的参考解法失效；保存时保留并标明失效状态，重新成功回放后更新校验哈希。
- 正式场景的运行时生成对象不作为作者数据；不能通过直接拖动生成 Prefab 绕过编辑器保存。

### 6.2 统一制作流程

```text
创建/打开 LevelDefinition
    → 编辑工作副本
    → 校验并定位问题
    → 从工作副本建立试玩快照
    → 在正式 LevelRunner 中试玩
    → 返回原工作副本继续编辑
    → Save 写入关卡 JSON
    → 参考解法回放通过
    → 加入 CampaignCatalog
    → 构建前校验
```

保存允许尚未完成但可序列化的关卡，以免丢失工作；试玩、加入正式目录和正式构建必须通过语义校验。未保存草稿自动备份到 `Library/SokobanDrafts`，重新打开工具或脚本重载后可恢复。编辑器撤销历史只保证当前编辑会话，草稿内容必须能跨重载恢复。

### 6.3 校验规则

**错误，阻止试玩/发布：**

- schemaVersion 不支持、行数/行长不符、未知地形符号、宽高越界。
- 玩家数量不是 1、没有目标插槽、箱子数少于目标数。
- 实体越界、位于 Wall/Void、玩家和箱子重叠、箱子相互重叠。
- 插槽和门重叠、多个插槽或多个门重叠、插槽/门位于 LowFriction。
- 玩家出生点位于门上；箱子可合法初始化在插槽或门上。
- 全关元素 ID 重复、门引用不存在、来源列表为空、来源重复、未知 Any/All 值。
- 正式关卡目录中 ID 重复、JSON 无法解析、引用的必需表现资源缺失。

**警告，不阻止保存/试玩：**

- 把所有门视为打开并忽略箱子时，玩家仍无法连通的可行走区域。
- 非目标位置的箱子处于由固定墙/地图外构成的直角死角。
- 开局已完成、辅助插槽没有被门引用、参考解法缺失或过期。

“校验通过”只代表结构合法，不代表谜题有解。首版无需通用求解器；正式关卡必须有通过共享规则内核回放的参考解法。

### 6.4 编辑与试玩隔离

- 原始 JSON、编辑工作副本、运行时 GameState 是三份不同对象，修改其中一份不能隐式修改另外两份。
- 试玩使用工作副本的深拷贝，未保存内容可以试玩，试玩完成不会写回箱子位置。
- Editor 适配层保存 SceneSetup、编辑器选中关卡与草稿标识，再进入专用 Bootstrap 场景。
- 使用 `EditorApplication.playModeStateChanged` 和 `SessionState`/Library 临时快照跨越 domain reload；编辑器专用桥接把快照交给正式 LevelRunner。
- 退出试玩后恢复此前场景与工作副本。涉及用户尚未保存的其他场景时使用 Unity 原生保存处理，不能默默覆盖。
- 打包运行时不得引用 `UnityEditor`、AssetDatabase 或 Library 路径；该桥接仅属于 Editor 程序集。

### 6.5 Agent 可调用的作者接口

编辑器的按钮和自动化命令必须调用同一组作者操作，例如 NewLevel、PaintTerrain、PlaceEntity、SetSocket、SetGateSources、Resize、Validate、Save、Playtest。接口名字可按代码风格调整，但职责保持一致。

实现一个“导入策划配方”入口，接收地图文本和实体配置，转换成同一编辑工作文档。实现 Agent 可以通过 Unity MCP/Editor 脚本调用这个入口批量建立本文关卡，再在窗口检查、保存、试玩。不能另建一个跳过校验或只供脚本使用的关卡加载器。

## 8. Unity 实现结构与表现时序

### 8.1 模块职责

| 模块 | 职责 | 不能负责 |
|---|---|---|
| LevelValidator | 格式、占格、连接及作者错误检查 | 用场景碰撞体猜地图 |
| RuleEngine | 移动、推动、滑行、供电、最终胜利解析 | 动画、相机、音效 |
| GameSession | 当前稳定状态、命令队列、History、计数 | 写回关卡初始 JSON |
| LevelRunner | 加载/卸载一关、装配规则和表现 | 每关单独硬编码规则 |
| BoardView | 由数据生成白模/正式模型，响应状态事件 | 决定通行性 |
| RobotPresenter | 三种动画、视觉朝向、推板接触、表情锚点 | 使用根运动改变网格位置 |
| CameraRig | 双视角、环绕、避障和输入方向参考 | 推动箱子或改变解法状态 |
| LevelEditor | 编辑副本、作者命令、保存、校验、试玩 | 维护另一套规则 |

Domain、Runtime、Editor、Tests 使用清晰程序集依赖。Domain 使用整数组合和集合，避免 UnityEngine 依赖，便于快速 EditMode 测试。保持模块数量适中，不需要 ECS、网络框架或通用事件总线。

### 8.2 建议的关键接口

```csharp
ValidationReport Validate(LevelDefinition definition);
GameState CreateInitialState(LevelDefinition definition);
MoveResolution Resolve(LevelDefinition definition, GameState state, Direction direction);
// MoveResolution: Accepted, RejectReason, NextState, OrderedMicrosteps
// Microstep: playerFrom/To、可选 crateId/from/to、供电变化、门变化
void LoadLevel(LevelDefinition definition, SessionMode mode);
void Present(MoveResolution resolution);
void Restore(GameState snapshot); // 取消旧表现并立即同步完整场景
```

这些是职责约定而非强制逐字复制的 API。RejectReason 至少能区分玩家阻挡、箱子目标阻挡、连推受阻；玩家提示保持简短，不显示程序枚举名。

### 8.3 动作时序

- 普通移动：初值 0.25 s；视觉转向先以不超过 0.08 s 对齐目标方向，再移动。转向不计步。
- 推动：先完成朝向对齐，再播放 0.60 s 的 Push。
- Push 的 `0.00–0.10 s`：机器人与箱子保持原位置，推板伸出。
- Push 的 `0.10–0.50 s`：机器人与箱子使用同一个归一化进度 `u`、同一个 `SmoothStep(u)`，各前进 1 m，维持接触。
- Push 的 `0.50–0.60 s`：推板收回。普通地面上的箱子和玩家已经到位。
- 若有额外滑行，从 t=0.50 s 起箱子继续播放各段轨迹，每额外格初值 0.12 s；机器人不继续移动，推板正常收回。
- 整条动作 Busy 时长为 `max(0.60, 0.50+0.12*额外滑行格数)`。
- 供电/门表现事件随对应 Microstep 到达格中心时播放；逻辑结果始终以 RuleEngine 预先解析的顺序为准。
- 短距离门开合初值 0.12 s。门关闭碰撞不会推挤角色，碰撞体仅用于镜头等辅助用途。
- 全部表现用可取消的时间轴/任务驱动。暂停、撤销、重开、切关必须能够停止旧回调，防止恢复后又被过期动画覆盖。
- 本版每次 Push 完整伸出和收回；“连续推箱保持推板伸出”留作后续打磨，不新增 PushHold 等资产依赖。

## 9. 与 Blender 共享的 robot-asset-v1 约定

### 9.1 模型与锚点

| 项目 | 约定 |
|---|---|
| Unity 朝向 | +Y 向上，+Z 为机器人正前方，+X 为机器人右侧 |
| 模型根 | `RobotRoot`，原点在地面投影中心，静止 Y=0 |
| 尺寸 | 静止宽约 0.70 m、深约 0.68 m、高约 0.80 m |
| 推板收回 | 正面位于局部 Z=0.36 m |
| 推板伸出 | 正面位于局部 Z=0.60 m，总行程 0.24 m |
| 接触高度 | 推板中心 Y=0.40 m，宽约 0.46 m、高约 0.20 m |
| 箱子对齐 | 箱子中心在前方一格 Z=1.0 m，后表面 Z=0.60 m |
| 气泡锚点 | `EmotionAnchor`，局部 `(0,1.05,0)`，跟随根、不跟随摆头 |
| 接触锚点 | `PushContact`，随推板移动，代表推板正面中心 |
| 相机锚点 | Unity 运行时在逻辑角色下创建，固定高度 0.55 m，独立于动画层 |

允许几何体细节有小幅艺术调整，但接触面的误差应 ≤0.01 m。调尺寸必须同时改两份文档和白模，不能只靠 Unity 导入后任意缩放补救。

### 9.2 三种动画与文件

资产目录交付：`ArtSource/Robot/Robot.blend`、`ArtSource/Robot/robot_asset_manifest.json`、`Assets/_Game/Art/Robot/Robot.fbx`、所需简单材质/贴图、正侧顶预览和三段动作预览。

采用一个连续烘焙时间轴导出，再在 Unity 按明确范围切成三条剪辑，减少多个机械物件 Action 分散导致遗漏的风险。采样 30 fps：

| Unity 剪辑名 | Blender/FBX 时间轴帧 | 时长 | 循环 |
|---|---|---|---|
| Idle | 0–60 | 2.00 s | 是 |
| Move | 70–100 | 1.00 s | 是 |
| Push | 110–128 | 0.60 s | 否 |

Push 接触帧=113，移动结束/开始收回帧=125。FBX 的时间原点必须经回读确认；若导出器偏移起点，manifest 记录实际帧区间，Unity 导入器按记录切片，不能凭记忆套范围。

- 三条动画都原地制作，RobotRoot 无位置、旋转、缩放动画；Unity 的 Root Motion 关闭。
- 导入采用适用于机械层级的 Generic 配置，保留节点层级，不启用会隐藏必需 Transform 的层级优化。
- 推箱使用受游戏动作进度控制的确定性剪辑采样，例如 Playables；不依赖动画事件来推进规则。
- 原地轮组转动可代表基础履带运动；首版不要求逐节履带模拟或履带材质滚动。模型动作必须来自 Blender 导出的机械动画。
- 表情气泡由 Unity Canvas/Sprite 绘制，不占用第四条机器人动画。
- 机器人白模必须提供相同锚点和 RobotPresenter 接口；正式 FBX 到位后替换视觉子树和资源引用，不改推箱逻辑。

## 10. 白模、美术和反馈

- 色彩：墙/机身浅灰，底座深蓝灰；通电青蓝，机器人识别色橙色。颜色同时辅以图标与线条状态。
- 地板保留清晰格缝；LowFriction 用不同粗糙度、边框和连续纹理区别普通地面，即使关闭 Bloom 也能看懂。
- 目标插槽使用双圈/目标图标；辅助插槽使用插头图标；已通电与未通电状态至少在形状/亮度上有区别。
- 门旁展示来源插槽编号和 Any/All 对应的简单图标说明，选中观察时高亮连接。
- 白模门和箱子轮廓要能从第三人称识别；门上部在俯视模式隐藏时保留明确的通行标记。
- 气泡：推不动显示“!”或疑问符号，约 0.7 s；通关显示 ✓，约 1.2 s；只保留一个气泡，完成反馈优先。
- 气泡面向实际渲染相机，切换相机不消失，使用图形资源或确认支持的字体，避免依赖系统彩色 emoji。
- 最低音效集合：移动、推动接触、箱子落位、通电/断电、受阻、完成、UI 点击。没有素材时可用简单合成占位音。
- 灯光采用一套 URP 基础照明、柔和阴影和少量 Bloom。先验证灰阶识别度，再增加发光效果。

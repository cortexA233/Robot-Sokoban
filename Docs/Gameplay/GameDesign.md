## 0. 产品目标与范围

本项目用于技术策划招聘 Take-home 测试。完整交付包含两项成果：**具备 2–3 张完整关卡的可玩游戏，以及完整可用的 Unity 内关卡编辑器**。当前正式目录为 L04–L12 共九关。场景、箱子和机关已接入空间站首批美术套件；主角复用已交付的履带机器人预制体。新增美术按配套生产需求分批制作，资产生产与正式关卡替换分别验收。关卡通过现有作者工具与数据链制作，游戏与编辑器共享规则内核。

**编辑器是最高优先级的正式交付物。** 评审者应能仅通过编辑器界面独立完成“创建 → 编辑 → 配置机关 → 校验 → 试玩 → 修改 → 保存 → 重新打开 → 加入关卡目录”，无需编写代码、手改 JSON、调用 MCP 或请求实现 Agent 代操作。编辑器未达到这个标准时，整个 Take-home 项目不能标记为完成。

## 1. 游戏定位与体验

### 1.1 一句话概念

玩家控制一台履带维修机器人，把能源箱送入空间站的供电插槽，借助临时供电打开道路，重新分配有限能源，最终点亮各区域的核心设施。

### 1.2 体验支柱

1. **操作可预测**：一条方向指令对应一次明确的网格动作；失败不改变谜题局面。
2. **能源可以挪用**：插槽既可能是最终目标，也可能是临时开路工具。
3. **观察方便**：第三人称提供空间感，俯视方便规划；切换镜头不会重置局面。
4. **试错轻松**：一次撤销回退整次推动及其引起的全部滑行、供电变化。
5. **制作过程可复用**：正式关卡、测试关与后续关卡使用同一编辑器和运行时。

### 1.3 游戏循环与完整流程

主菜单 → 开始/继续或选择关卡 → 观察和推动 → 所有目标插槽通电 → 成绩结算 → 下一关/重开/选关。关卡使用顺序号/稳定 ID 识别；通用规则在操作说明页按需查看。

- 主菜单：开始、关卡选择、设置、退出。
- 设置仅需要主音量、鼠标灵敏度、反转垂直镜头；即时生效并保存。
- HUD：关卡名、已通电目标数/总数、移动次数、推动次数、视角切换/撤销/重开提示。
- 结算：关卡完成文案、移动/推动统计、下一关、重玩、选关；最后一关显示“空间站已重启”。
- 首次试玩的设计目标：L01 约 1–3 分钟，L02 约 3–6 分钟，L03 约 5–8 分钟。时间是待试玩调整的目标，不是已经测出的结果。
- 通关不要求走进额外出口；全部目标插槽稳定通电即完成。

## 2. 统一术语、坐标与空间约定

| 名称 | 定义 |
|---|---|
| Cell | 一个整数坐标 `(x,z)` 的棋盘格 |
| Terrain | 格子的基础类型：Void、Floor、Wall、LowFriction |
| EnergyCrate | 能被机器人推动一格并可能继续滑行的能源箱 |
| CargoCrate | 同样可推动和滑行的普通箱，不供电，也不要求归位 |
| PowerSocket | 能源箱占据时通电的插槽；普通箱与玩家占据时不供电 |
| GoalSocket | `isGoal=true` 的 PowerSocket，参与通关条件 |
| UtilitySocket | `isGoal=false` 的 PowerSocket，只作为机关电源 |
| PowerGate | 根据关联插槽的供电状态打开的门，占据一格 |
| MoveCommand | 一个世界方向 N/E/S/W 的完整逻辑操作 |
| Microstep | 一次命令中的初始位移或一次额外箱子滑行 |
| SettledState | 整条命令及全部滑行解析完后的稳定局面 |
| LevelDefinition | 关卡设计数据，保存地形、初始摆放、连接、文案 |
| GameState | 当前玩家/箱子位置及计数；不覆盖关卡初始数据 |

空间规范：

- 一个格子边长 `1.0 m`，地板顶面为 Unity 世界 `Y=0`。
- `(x,z)` 对应世界中心 `(x,0,z)`；格子边界为中心 ±0.5 m。
- `N=(0,+1)`、`E=(+1,0)`、`S=(0,-1)`、`W=(-1,0)`。
- 地图宽高包含边界；坐标从左下角 `(0,0)` 开始。
- 文本图和 `terrainRows` 从最北一行写到最南一行：第 r 行对应 `z=height-1-r`。
- 玩家和箱子的逻辑位置使用整数格坐标；Transform、碰撞体和动画不能反向决定占格。
- 地板固定单一高度；装饰可以有高度，但不形成第二层可行走区域。
- 箱子尺寸 `0.80 × 0.80 × 0.80 m`，根节点在底面中心，视觉中心 Y=0.40。
- 机器人静止包围盒约 `宽0.70 × 深0.68 × 高0.80 m`，详细接触尺寸见第 9 节。

## 3. 操作与双视角

### 3.1 默认输入

| 输入 | 行为 |
|---|---|
| W/A/S/D | 镜头相对的四方向网格移动；面对箱子时尝试推动 |
| 方向键 | 固定世界方向，↑=N、→=E、↓=S、←=W，适合精确操作 |
| 鼠标移动 | 第三人称模式下环绕观察；不改变机器人格坐标 |
| 鼠标滚轮 | 第三人称调整距离；俯视调整正交缩放 |
| V | 切换第三人称/俯视 |
| Z | 撤销最近一次成功命令 |
| R | 重开本关，清空本轮计数和撤销栈 |
| Esc | 暂停/返回；暂停时释放鼠标 |

- 第三人称游玩锁定鼠标；俯视、暂停、主菜单、结算释放鼠标，俯视可点击 HUD。编辑器 UI 不接收游戏移动输入。
- 同时按两个移动方向不形成斜走；以最近按下的有效方向为准。
- 按下立即尝试一格；持续按住先等待 0.25 s，再在上一动作完成后持续步进。不积压多条过期方向命令。
- 新按键最多缓存一个待执行方向；无效推动不增加计数，失败表情有 0.5 s 冷却。
- 重开、撤销、切关时清空输入缓存和长按状态，需再次按键才开始新动作。

### 3.2 第三人称方向映射

1. 使用镜头绕世界 Y 轴的轨道 yaw，而不是机器人朝向，确定当前相机前方。
2. 将 yaw 量化成最近的 N/E/S/W；W 对应该方向，S 相反，A/D 为左右各转 90°。
3. 扇区切换使用 8° 滞回：从当前扇区中心偏离超过 53°才切到相邻扇区，减少 45°边界抖动。
4. 一个按住的移动键在按下时锁定世界方向，直到松开；环绕观察不会使同一次长按突然转弯。
5. HUD 显示小型北向标记；方向键始终按世界方向解释。
6. V 切换时清掉尚未开始的移动输入；正在执行的命令继续，新模式需重新按下移动键。

### 3.3 镜头规格

**第三人称**：透视，FOV 55°；围绕逻辑玩家跟随位置上方 0.55 m 的独立目标旋转，默认距离 4.8 m、可调 3.0–6.0 m，俯角初值 48°、限制 30–65°。鼠标水平可环绕 360°。角色转身不能强制把相机转到背后；初始环绕方向由出生朝向决定。v0.5.1 按用户反馈取消局部剔除，始终完整显示墙体和门上层，保留原模型比例。

目标对象跟随玩家表现位置的平移，但不能继承头部摆动、机身前倾或推板动作。可用 Cinemachine Third Person Follow 加独立旋转目标处理环绕和避障；不要直接跟随会随移动旋转的模型节点。

**默认俯视**：开始游戏、选关、下一关和编辑器试玩均以正交俯视进入；固定世界北方在屏幕上方，相机看向 `-Y`，屏幕上方为 `+Z`。初始居中棋盘，在 HUD 中央净空区完整显示地图；`orthographicSize=max((height/2+0.35)/0.62,(width/2+0.35)/(aspect*0.92))`。窗口比例变化时全图模式重新取景；滚轮可缩放，缩小视野时以玩家为跟随中心，并将中心限制在地图范围内。暂停恢复、撤销和本关重开保留玩家选择的视角；新载入关卡恢复默认俯视。

**切换**：V 在移动、推箱和滑行途中都能使用，立即开始镜头切换。采用约 0.25 s 的位置/旋转过渡；透视/正交投影在过渡末明确切换。不能依赖切换镜头重新载入关卡。正在进行的逻辑动作不改变方向或终点。

**遮挡**：第三人称始终保留完整墙体和门结构，使用完整墙体/关闭门碰撞代理供 Cinemachine 避障，不随镜头位置进行局部隐藏、淡出或延迟恢复。仅俯视模式隐藏全部上层墙体和门结构、将代理缩至 0.24 m 基座高度，并保留连接与门通行地标；切回第三人称立即恢复完整几何和代理。逻辑墙格和门规则不变，机器人、箱子、插槽不作为镜头碰撞障碍。

## 4. 游戏规则：唯一判定依据

以下规则必须同时用于正式游玩、编辑器试玩、测试和参考解法回放。不得为某一张关卡写特例。

### 4.1 基础移动和箱子

- 箱子分 Energy（能源箱）与 Cargo（普通箱）。两者共享占格、推动、滑行和撤销规则；普通箱以棕色箱体及顶部/四侧交叉支架辨识。

- 一条命令移动玩家一格；成功推动时，玩家进入箱子的旧格，箱子先前进一格。
- Void、Wall、边界外不可进入。封闭门不可进入。只能同时推动一个箱子。
- 两箱相邻时不能连推，不能拉箱、斜推、抬箱、堆叠或掉出地图。
- 如果玩家前方被阻挡，或箱子第一目标格不合法，整个命令失败，局面和计数不变。
- 失败时机器人可以在表现层朝向输入方向，并显示表情；这不是一次逻辑移动。
- 普通成功移动：移动数 +1。成功推动：移动数 +1、推动数 +1。额外滑行不增加任何计数。
- 一次动作的所有逻辑变化先计算完成，再交给表现层播放；表现层播放时不接受第二条逻辑动作。

### 4.2 供电插槽

- 每个插槽占一个普通 Floor 格；能源箱位于该格时通电，移开后断电。
- 所有能源箱等价；首版不做颜色匹配、容量或耗电。
- 目标插槽和辅助插槽都可以为门供电。目标插槽通电后仍允许移走箱子。
- `isGoal=true` 的插槽全部通电才算完成；至少要有一个目标插槽。
- 不要求所有辅助插槽同时通电；可以有多于目标插槽数量的箱子。
- 基础校验要求能源箱数不少于目标插槽数；普通箱不计入能源供给。插槽总数可以大于能源箱数，这是挪用能源谜题的基础。
- 普通箱可以占据插槽但不供电，完成时无需归位；停在不再使用的固定死角可以是合法解法。
- 本版插槽只放在 Floor 上，不能与 LowFriction 或门重叠。

### 4.3 受电门

- 一个门关联 1 个或多个插槽 ID，编辑器支持 `Any`（任一通电）和 `All`（全部通电），默认 Any。
- 一个插槽可以控制多个门；空连接和失效引用是校验错误。
- 门的电源状态仅由关联插槽计算，门不会向其他设备输出电源。
- 定义：`powered = Any/All(来源插槽通电)`。
- 定义：`effectiveOpen = powered || 门格被玩家或箱子占据`。
- 断电且无人占据时立即逻辑关闭；门格内有人或箱子时保持打开，直到格子腾空，避免夹住物体。
- 通行检查使用本次 Microstep 开始时的 effectiveOpen，先完成该步全部占格交换，再重算电源和门。
- 因此，箱子占据断电门时，玩家仍可把它推出门，同时进入它的旧门格；门继续保持打开，直到玩家也离开。这个行为属于明确规则。
- 门开合动画不延迟逻辑判定，不得用 Animator 状态或物理触发器判断是否通电。
- 门初始若被箱子占据，其 effectiveOpen=true；玩家初始生成点不能设在门上，以减少不易理解的开局。
- 门朝向只用于造型，不增加单向通行规则。

### 4.4 低摩擦轨道

低摩擦轨道是 `LowFriction` 地形，视觉可做成带方向纹理的光滑运输板；首版沿本次推动方向滑行，纹理方向不影响逻辑。

1. 只有箱子受低摩擦影响，履带机器人仍然一格一格走。
2. 箱子完成第一格推动后，如果所在格是 LowFriction，就继续尝试沿原方向前进一格。
3. 只要当前格仍是 LowFriction 且下一格合法，就继续；进入无转向板的普通 Floor、插槽或打开的门格后停止。进入转向板则按第 4.4.1 节改变方向。
4. 如果下一格是墙、Void、边界外、关闭门、其他箱子或玩家，停在当前格。
5. 受阻后没有连锁推箱、反弹、转向或延迟滑行；以后必须再次收到推动命令才会移动。
6. 玩家只进入原箱子格，不跟随箱子滑行。
7. 插槽和门都不能叠加在 LowFriction 上；停在插槽时立即按占格计算供电。
8. 如果箱子从插槽被推上轨道，第一格交换后就断电；后续滑行遇到该电源控制的关闭门，必须停住。
9. 一次推动加整段滑行是一条命令、一次撤销。包含转向板的自动路线按活动箱位置与方向检测循环；重复时整条命令拒绝，原局面、计数和历史不变。

### 4.4.1 固定转向板（v0.3.0）

- `RedirectorDefinition` 放在普通 Floor 上，保存固定 N/E/S/W 方向，与插槽、门、其他转向板互斥；本身不需要供电。
- 两类箱子进入板格后改沿箭头尝试继续走一格；接轨道则持续沿新方向滑行，接另一块板则再次转向。普通地板、插槽和开门格均为停靠点。
- 出口受阻时停在板上。移走障碍不会自动启动；下次玩家可从任一合法方向将箱子推离板，再按新落点解析。
- 机器人、初始放置、GM 移位不触发自动运输。一次推动与全部转弯仍只计一次移动/推动，一次撤销恢复整条命令。
- 自动路线循环返回 `TransportCycle`，整条指令拒绝；运行提示说明原因。完整关卡与制作说明见 [转向运输方案](RedirectorLevelPlan.md)。

### 4.5 解析顺序

```text
TryResolve(definition, settledState, direction)
  1. 用当前占格重算电源和门的 effectiveOpen。
  2. 检查玩家下一格。
  3. 如果有箱子，检查箱子第一目标格；不合法则返回 Rejected。
  4. 在状态副本中原子更新玩家/箱子位置，记录第一条 Microstep。
  5. 重算供电和门，把变化附在该 Microstep 上。
  6. 若当前格有转向板，更新运输方向；否则仅在 LowFriction 上继续。逐格检测循环、通行与占格，每格重新计算供电；受阻或到达普通停靠格即停止。
  7. 更新一次移动/推动计数，仅在最终稳定局面判定完成。
  8. 返回完整的新状态及有序表现事件；原始状态保持不变。
```

阶段 1/3 的通行检查都基于各自 Microstep 开始的状态；如果门在同一步结束才关闭，不能追溯否决已合法完成的那一步。

### 4.6 撤销、重开、暂停与完成

- History 记录每条成功命令之前的玩家位置、带稳定 ID 的箱子位置、移动/推动数和恢复展示需要的朝向。
- 供电和门状态由恢复后的占格重新计算，不另存容易失配的副本。
- Z 在动作中也有效：取消表现任务和输入队列，回到这条命令之前的完整快照，机器人动画归位。
- R 在动作中也有效：取消所有表现任务，回到 LevelDefinition 的初始状态，不改变当前视角模式。
- 暂停冻结移动、动画、滑行和计时；恢复继续同一动作。UI 操作不进入 History。
- 镜头切换、环绕、失败输入、表情和音效都不进入 History。
- 完成逻辑只在最终稳定状态计算；完成 UI 在对应表现事件全部结束后出现，避免滑行中间短暂满足目标就结算。
- 结算界面允许 Z 回退继续解题；已解锁的下一关不重新锁定。关卡选择返回、切关和重新进入则开新局。
- 通关记录按关卡 ID 保存；最佳成绩按“推动数优先、移动数次之”保存同一局的成绩对，不分别拼接两局数据。不要求计算最优解或星级。

### 5.1 配方格式

## 6. 从第一天建立关卡编辑器

本节定义首版**完整可用编辑器**的范围。完成必须覆盖这一版游戏的全部地形、实体、机关参数和关卡流程；通用求解器、任意资产浏览器等扩展不属于这个定义。所有标为必需的功能都要有真实可操作的界面和可观察结果。

### 6.1 窗口与工具

入口：`Sokoban_Tools > Level Editor`。使用 UI Toolkit EditorWindow，配合 SceneView 网格交互。

| 区域 | 必需功能 |
|---|---|
| 顶栏 | 新建、打开、保存、另存为/复制关卡、校验、试玩并录制、关卡目录、帮助 |
| 左侧画笔 | Floor、Wall、Void、LowFriction、玩家、能源箱、普通箱、辅助插槽、目标插槽、门、固定转向板、选择 |
| 中央 SceneView | 网格、坐标、落点预览、选中轮廓、拖刷、机关连线 |
| 右侧属性 | ID、格坐标、朝向、isGoal、Any/All、来源插槽列表、提示/完成文案 |
| 底栏 | 当前尺寸、未保存状态、错误/警告列表、点击定位问题格 |

基本交互：左键放置/选取，拖拽连续刷地形，同层实体放置直接覆盖；右键不编辑关卡；Q/E 旋转门、玩家和装饰朝向；Ctrl+Z/Ctrl+Y 撤销/重做；Ctrl+S 保存；中键/Alt 操作保留 SceneView 导航习惯，避免抢占导航输入。

完整性要求：

- 支持 5–32 格的宽高；默认新图 9×9。新图可通过“一键生成边界墙”建立最外圈墙体。
- 地形层、机关层、动态实体层分别处理，同层实体放置直接替换，合法跨层叠放保留。单个对象通过属性栏删除；不提供擦除画笔或擦除层选择。
- 涂 Wall/Void 时若该格有实体，预览说明会删除该格上的实体；一次刷操作及相关删除属于同一撤销组。
- 删除插槽时，同时删除门中的对应引用；变成空连接的门显示错误，直到修复。
- 缩图前显示将裁掉的元素数，确认后在同一撤销组处理越界实体和引用。扩图新增区域为 Void。
- 一个拖刷手势是一条编辑撤销；单次属性编辑是一条撤销；不能每帧刷出重复对象。
- 已放置实体可重新选择、移动到另一合法格、修改属性、旋转或删除；不能只支持放置后重建整关。
- 插槽来源通过列表勾选或场景点选配置，显示连接线和可读名称；ID 自动生成，常规使用无需手输内部标识。
- 保存/打开窗口提供默认关卡目录；另存为/复制关卡分配新的关卡 ID，原关卡内容不被覆盖。
- 改变棋盘时使已记录的参考解法失效；保存时保留并标明失效状态，重新试玩通关、录制并保存新的证明。
- 正式场景的运行时生成对象不作为作者数据；不能通过直接拖动生成 Prefab 绕过编辑器保存。

### 6.2 统一制作流程

```text
创建/打开 LevelDefinition
    → 编辑工作副本
    → 校验并定位问题
    → 从工作副本建立试玩快照
    → 在正式 LevelRunner 中试玩
    → 返回原工作副本继续编辑
    → Save 写入关卡 JSON
    → 录制解法验证通过
    → 加入 CampaignCatalog
    → 构建前校验
```

保存允许尚未完成但可序列化的关卡，以免丢失工作；试玩、加入正式目录和正式构建必须通过语义校验。未保存草稿自动备份到 `Library/SokobanDrafts`，重新打开工具或脚本重载后可恢复。编辑器撤销历史只保证当前编辑会话，草稿内容必须能跨重载恢复。

### 6.3 校验规则

**错误，阻止试玩/发布：**

- schemaVersion 不支持、行数/行长不符、未知地形符号、宽高越界。
- 玩家数量不是 1、没有目标插槽、能源箱数少于目标数、未知箱型或 v1 数据包含普通箱。
- 实体越界、位于 Wall/Void、玩家和箱子重叠、箱子相互重叠。
- 插槽和门重叠、多个插槽或多个门重叠、插槽/门位于 LowFriction。
- 玩家出生点位于门上；箱子可合法初始化在插槽或门上。
- 全关元素 ID 重复、门引用不存在、来源列表为空、来源重复、未知 Any/All 值。
- 正式关卡目录中 ID 重复、JSON 无法解析、引用的必需表现资源缺失。

**警告，不阻止保存/试玩：**

- 把所有门视为打开并忽略箱子时，玩家仍无法连通的可行走区域。
- 非目标位置的箱子处于由固定墙/地图外构成的直角死角。
- 开局已完成、辅助插槽没有被门引用、参考解法缺失或过期。

“校验通过”只代表结构合法，不代表谜题有解。首版无需通用求解器；正式关卡必须有通过共享规则内核回放的参考解法。

### 6.4 编辑与试玩隔离

- 原始 JSON、编辑工作副本、运行时 GameState 是三份不同对象，修改其中一份不能隐式修改另外两份。
- 试玩使用工作副本的深拷贝，未保存内容可以试玩，试玩完成不会写回箱子位置。
- Editor 适配层保存 SceneSetup、编辑器选中关卡与草稿标识，再进入专用 Bootstrap 场景。
- 使用 `EditorApplication.playModeStateChanged` 和 `SessionState`/Library 临时快照跨越 domain reload；编辑器专用桥接把快照交给正式 LevelRunner。
- 退出试玩后恢复此前场景与工作副本。涉及用户尚未保存的其他场景时使用 Unity 原生保存处理，不能默默覆盖。
- 打包运行时不得引用 `UnityEditor`、AssetDatabase 或 Library 路径；该桥接仅属于 Editor 程序集。

### 6.5 Agent 可调用的作者接口

编辑器的按钮和自动化命令必须调用同一组作者操作，例如 NewLevel、PaintTerrain、PlaceEntity、SetSocket、SetGateSources、Resize、Validate、Save、Playtest。接口名字可按代码风格调整，但职责保持一致。

实现一个“导入策划配方”入口，接收地图文本和实体配置，转换成同一编辑工作文档。实现 Agent 可以通过 Unity MCP/Editor 脚本调用这个入口批量建立本文关卡，再在窗口检查、保存、试玩。不能另建一个跳过校验或只供脚本使用的关卡加载器。

自动化入口是作者工具的补充。最终验收必须包含从空白图开始的纯界面操作；只有脚本能建图、只有 Inspector 能改字段或只有批处理能保存，均不满足本版编辑器交付要求。

### 6.7 参考解法录制与回放

- “试玩并录制”从当前工作副本的初始局面开始新会话，不在任意中间局面开始录制。
- 只记录共享规则内核接受的 N/E/S/W 命令；一次推动及整段滑行只记录一个字母。拒绝输入、镜头操作和表情不记录。
- 试玩中撤销同步移除最后一条录制命令；重开清空录制序列。录制序列必须始终能从该关初始状态重放到当前局面。
- 完成后提供“保存为参考解法”，写入第7.3节的记录格式和当前工作副本哈希；未通关也可保留为普通试玩记录，但不能显示为通关证明。
- v0.4.1 删除手动回放入口。目录和构建自动使用相同 LevelDefinition 和 RuleEngine 验证录制指令、通关状态、终点和计数；失败会报告原因。
- 保存关卡/解法时绑定同一份内容版本；修改关卡使证明过期。构建前对正式目录全部重放并报告，失败则阻止正式构建。
- 工具必须提供这些操作按钮；评审者无需手工拼接解法字符串或编辑解法 JSON。

### 6.8 面向其他策划的界面反馈

- 默认打开时展示操作提示或示例关卡入口，不要求用户猜菜单和输入顺序。
- 字段有名称、合法范围和简短用途说明；Any/All 对应“任一来源供电/全部来源供电”。
- 鼠标指向棋盘显示实际落格位置；非法放置给出原因；编辑属性时不触发游戏热键。
- 校验错误、保存失败和试玩失败在工具窗口内显示可读信息，不能只把异常抛到 Console。
- 未保存标记与当前文件路径始终可见；打开另一关或关闭窗口时可以保存、放弃或取消操作。
- 关卡目录中分别标明正式关和开发测试关，LAB01 可快速打开但默认不进入正式关卡选择。

### 7.2 schemaVersion=1 示例：L02

以下是完整的核心数据示例。`terrainRows` 只允许 `# . ~ _`，其中 `_`=Void；实体由数组描述，不放进 terrainRows。

```json
{
  "schemaVersion": 1,
  "id": "L02",
  "width": 13,
  "height": 9,
  "gridSize": 1.0,
  "terrainRows": [
    "#############",
    "#.....#.....#",
    "#.....#.....#",
    "#.....#.....#",
    "#...........#",
    "#.....#.....#",
    "#.....#.....#",
    "#.....#.....#",
    "#############"
  ],
  "playerSpawn": { "x": 2, "z": 2, "facing": "E" },
  "crates": [
    { "id": "crate_01", "x": 3, "z": 2 },
    { "id": "crate_02", "x": 3, "z": 4 }
  ],
  "sockets": [
    { "id": "socket_s", "x": 4, "z": 2, "isGoal": false },
    { "id": "socket_a", "x": 9, "z": 4, "isGoal": true },
    { "id": "socket_b", "x": 9, "z": 2, "isGoal": true }
  ],
  "gates": [
    {
      "id": "gate_01", "x": 6, "z": 4, "facing": "E",
      "powerMode": "Any",
      "sourceSocketIds": ["socket_s", "socket_a"]
    }
  ],
  "decorations": []
}
```

DTO 采用可序列化类和数组，不在文件里保存 GameObject 引用或 Dictionary。运行时在校验后建立按格/按 ID 的索引。纯规则模块不依赖 JSON 库；JSON 适配器可以使用 Unity JsonUtility，但必须检测缺失必需字段和非法枚举，不能把缺失值默认为合法地图。

补充字段约定：

- decorations 每项包含 `id、typeId、x、z、facing`，均为非阻挡装饰；首版允许空数组。装饰不能参与供电和通行判定。
- playerSpawn 是单个对象；编辑器内部可临时为空，发布数据必须存在。
- gridSize 固定为 1.0，其他值校验失败。改变比例需要升级两份文档中的共享约定。
- 所有枚举在 JSON 中采用本文字符串；不支持的 schemaVersion 明确报错，不自动猜测迁移。
- 当前正式关卡使用稳定的 L04–L12 ID，已删除的 L01–L03 不重新分配。复制关卡生成新 ID，不覆盖原关。

**箱型扩展格式：** v2 引入显式箱型；当前新建地图使用 `schemaVersion=3`，每个 crate 都必须包含 `kind: "Energy"` 或 `kind: "Cargo"`。例如 `{ "id": "crate_X", "x": 3, "z": 3, "kind": "Cargo" }`。类型随副本、草稿、试玩快照保存，参与内容哈希；修改箱型会使旧解法过期。

读取 v1 时显式赋予能源箱语义，仍保留版本1；写回和计算哈希时保持原字段布局，因此未修改的旧关卡参考解法继续有效。给旧图放普通箱或把箱型改为 Cargo 时至少升级为版本2，已有 v3 不降级，可整体撤销。v1 不接受 kind 字段，v2 不接受缺失/错误类型的 kind，未知版本明确报错。

**转向板格式：** v3 要求 `redirectors` 数组，元素为 `{ "id": "redirector_1", "x": 3, "z": 4, "facing": "E" }`。空数组合法，缺字段、未知方向或与其他机关重叠会报错。新图为 v3；给 v1/v2 地图添加板时升级，可撤销。旧图读取时在内存显式补空数组，按原 schema 写回并计算哈希，不为未修改旧图增加字段；已有参考解法继续有效。带转向板的数据拒绝以 v1/v2 保存，修改方向会使解法哈希过期。

v0.6.0 移除逐关 `title`、`briefing`、`completionText` 字段和对应编辑/UI 控件。机制 schemaVersion 仍为 1/2/3；读取仅兼容丢弃这三项旧文案，写出时不恢复，其他字段保持严格校验。旧内容哈希失效，正式/实验关卡的证明必须回放后重新生成。

### 7.3 参考解法与进度

`Content/Solutions/L02.solution.json` 建议结构：

```json
{
  "schemaVersion": 1,
  "levelId": "L02",
  "commands": "ENWNEEEEEEWWWSSSWNNWNEEEENESSWSE",
  "expectedMoves": 32,
  "expectedPushes": 16,
  "expectedPlayer": { "x": 8, "z": 2 },
  "expectedCrateCells": [{ "x": 9, "z": 2 }, { "x": 9, "z": 4 }]

```

编辑器试玩通关录制时记录源 LevelDefinition 的规范化内容哈希；示例尚未包含实现时生成的哈希。任何内容变化均使证明过期，需要重新试玩通关并录制；目录与构建自动验证当前证明。

玩家进度保存在 `Application.persistentDataPath/player-progress.json`（进度格式 v1），按稳定 ID 和规范内容哈希记录最近关卡及最佳成绩对；步数少优先，同步数时推动少优先，二者来自同一次正式通关。“继续游戏”从最近关卡起点开始，全关可选。目录排序不影响记录；删除的关卡不作为继续入口；同 ID 内容改变时旧成绩不用于新版，重新完成后替换。原子写入并保留 `.bak`；损坏时回退备份或空记录，覆盖前保留不可读原文件，失败时保留内存结果并允许重试。作者试玩、非正式加载和带 GM 修改的局面不写正式成绩。主音量、灵敏度、镜头反转继续使用原 PlayerPrefs 键。

## 8. Unity 实现结构与表现时序

### 8.1 模块职责

| 模块 | 职责 | 不能负责 |
|---|---|---|
| LevelValidator | 格式、占格、连接及作者错误检查 | 用场景碰撞体猜地图 |
| RuleEngine | 移动、推动、滑行、供电、最终胜利解析 | 动画、相机、音效 |
| GameSession | 当前稳定状态、命令队列、History、计数 | 写回关卡初始 JSON |
| LevelRunner | 加载/卸载一关、装配规则和表现 | 每关单独硬编码规则 |
| BoardView | 由数据生成白模/正式模型，响应状态事件 | 决定通行性 |
| RobotPresenter | 三种动画、视觉朝向、推板接触、表情锚点 | 使用根运动改变网格位置 |
| CameraRig | 双视角、环绕、避障和输入方向参考 | 推动箱子或改变解法状态 |
| FeedbackPresenter | 根据表现事件播放音效、粒子和提示，管理反馈播放和清理 | 修改占格、供电、History或胜利条件 |
| LevelEditor | 编辑副本、作者命令、保存、校验、试玩 | 维护另一套规则 |

Domain、Runtime、Editor、Tests 使用清晰程序集依赖。Domain 使用整数组合和集合，避免 UnityEngine 依赖，便于快速 EditMode 测试。保持模块数量适中，不需要 ECS、网络框架或通用事件总线。

### 8.2 建议的关键接口

```csharp
ValidationReport Validate(LevelDefinition definition);
GameState CreateInitialState(LevelDefinition definition);
MoveResolution Resolve(LevelDefinition definition, GameState state, Direction direction);
// MoveResolution: Accepted, RejectReason, NextState, OrderedMicrosteps
// Microstep: playerFrom/To、可选 crateId/from/to、供电变化、门变化
void LoadLevel(LevelDefinition definition, SessionMode mode);
void Present(MoveResolution resolution);
void Restore(GameState snapshot); // 取消旧表现并立即同步完整场景
```

这些是职责约定而非强制逐字复制的 API。RejectReason 至少能区分玩家阻挡、箱子目标阻挡、连推受阻；玩家提示保持简短，不显示程序枚举名。

### 8.3 动作时序

- 普通移动：初值 0.25 s；视觉转向先以不超过 0.08 s 对齐目标方向，再移动。转向不计步。
- 推动：先完成朝向对齐，再播放 0.60 s 的 Push。
- Push 的 `0.00–0.10 s`：机器人与箱子保持原位置，推板伸出。
- Push 的 `0.10–0.50 s`：机器人与箱子使用同一个归一化进度 `u`、同一个 `SmoothStep(u)`，各前进 1 m，维持接触。
- Push 的 `0.50–0.60 s`：推板收回。普通地面上的箱子和玩家已经到位。
- 若有额外滑行，从 t=0.50 s 起箱子继续播放各段轨迹，每额外格初值 0.12 s；机器人不继续移动，推板正常收回。
- 整条动作 Busy 时长为 `max(0.60, 0.50+0.12*额外滑行格数)`。
- 供电/门表现事件随对应 Microstep 到达格中心时播放；逻辑结果始终以 RuleEngine 预先解析的顺序为准。
- 短距离门开合初值 0.12 s。门关闭碰撞不会推挤角色，碰撞体仅用于镜头等辅助用途。
- 全部表现用可取消的时间轴/任务驱动。暂停、撤销、重开、切关必须能够停止旧回调，防止恢复后又被过期动画覆盖。
- 本版每次 Push 完整伸出和收回；“连续推箱保持推板伸出”留作后续打磨，不新增 PushHold 等资产依赖。

### 8.4 已安装插件的分工

插件用于落实既定表现方案。棋盘规则、LevelDefinition格式、参考解法、E01–E12编辑器完整性和Take-home交付门槛保持一致。

| 插件/系统 | 当前确认 | 本项目用途 | 实现边界 |
|---|---|---|---|
| Cinemachine | manifest：2.10.7 | 第三人称环绕/跟随、避障，配合俯视虚拟相机和Brain管理输出 | CameraRig独占镜头模式、方向参考和投影设置 |
| DOTween / DOTween Pro | 文件已导入；发行版本在接入时从Utility Panel记录，不能把DLL的1.0.0.0文件版本当发行版本 | 可取消的动作时间进度、门模型开合、菜单和气泡的过渡 | 只改变表现；移动终点和中间路径来自MoveResolution |
| Blender剪辑 | robot-asset-v1 | Idle、Move、Push内部机械动作 | RobotPresenter按共同动作时钟采样，保持既定帧范围和接触点 |

**Cinemachine：** 第三人称与俯视各有独立虚拟相机配置，输出由一个Brain管理。环绕目标独立于机器人模型动画；切换仍遵守第3.3节的投影与方向规则。若添加轻微震动，优先通过Cinemachine Impulse叠加；DOTween不直接写实际Camera的Transform/FOV。

**DOTween：** GameSession提交逻辑结果后，表现层创建属于这次命令的根Sequence或时间进度Tween。让一个线性时间值 `t` 从0走到动作总时长，再按第8.3节计算各物体位置和Push剪辑采样时间；机器人与箱子共享同一进度，SmoothStep只在位移计算中应用一次。不要给两个对象各启动一个可能延迟不同的独立推动Tween。

DOTween Pro的可视化组件适合菜单、固定UI元素和纯视觉装饰。动态箱子路径必须由已解析的格子路径生成；DOTween Path不作为关卡寻路、碰撞或滑行判定来源。正式机器人的PushSlide、HeadYaw、轮轴由Blender剪辑驱动，不能再叠加一个写同一属性的DOTweenAnimation。

**反馈：** FeedbackPresenter根据已确认的表现事件，通过Unity音源、粒子和灯光组件播放接触、落位、通断电、受阻与完成效果。供电和门的稳定视觉状态由BoardView维护；短促的附加效果尽量使用独立灯光/粒子/覆盖层，避免争写同一材质属性。

失败表情和通关气泡的文本/图形由游戏UI决定，DOTween负责其出现和淡出，FeedbackPresenter播放对应声音。关闭附加音效与光效时，核心游戏和关卡编辑器仍应可用。

### 8.5 插件的取消、恢复与暂停协议

每次命令/每次关卡加载都有代次标识；延迟回调执行前确认仍属于当前代次。取消按以下顺序处理：

1. 使旧代次失效，停止接受旧回调，清空待执行输入。
2. 对当前会话拥有的DOTween根Tween/Sequence执行 `Kill(false)`，清理引用。`OnKill`只做资源清理；不能用 `Complete` 或 `Kill(true)`完成一个正在被撤销的动作，也不能用全局KillAll影响其他UI。
3. 停止并清理当前会话拥有的音源、粒子与气泡，重置附加效果改变的视觉属性。
4. 取消当前Blender剪辑采样任务，按需要回到Idle起点；复用池对象前同样执行清理。
5. 最后从目标GameState快照完整刷新玩家、箱子、门、插槽及HUD，确保视觉状态与撤销目标局面一致。

游戏内Tween和反馈使用受游戏暂停控制的时间；菜单过渡可使用独立时间。实际验证所用音源、粒子和过渡的暂停与恢复行为。

如果使用 `SetLink`，链接根Sequence/根Tween到其会话宿主；加入Sequence的子Tween不单独依赖SetLink清理。切关/停止试玩仍显式取消会话拥有的全部表现。Safe Mode是辅助保护，不替代生命周期管理。有关DOTween取消与Sequence控制的API语义参见[官方文档](https://dotween.demigiant.com/documentation.php)。

### 9.4 机器人运行时集成约定

1. **维护现有包装。** `Assets/Resources/prefabs/gameplay/player/PlayerActor.prefab` 已作为游戏外层嵌套Robot.prefab。玩家输入/格坐标/朝向控制放在外层或由GameSession持有；RobotPresenter位于 `Assets/Scripts/Player/`，只持有视觉对象引用。保留Robot美术预制体的GUID和子层级。
2. **分清动画根。** 预制体最外层Robot持有Animator，内层RobotRoot保持静止局部变换。当前剪辑以Robot为绑定根，曲线路径均以 `RobotRoot/...` 开头，包含RobotRoot本身的常量曲线；不能把Animator挪到PlayerActor/RobotRoot，或用内层RobotRoot承载网格位移。
3. **绑定现有剪辑。** 从Controller持有的引用/序列化AnimationClip字段绑定Idle、Move、Push，不在Player构建中调用AssetDatabase加载FBX。Controller没有Speed/IsPushing/Push触发器，不假定这些参数存在。使用受第8.3节共同时间值驱动的Playables实现采样，并保证只有一套动画驱动器写机械节点，不能让Controller自动播放与手动采样相互覆盖。
4. **精确寻址锚点。** 相对于视觉根Robot，气泡路径为 `RobotRoot/EmotionAnchor`，推板接触路径为 `RobotRoot/PushSlide/PushContact`；相对于内层RobotRoot则分别为 `EmotionAnchor` 和 `PushSlide/PushContact`。相机目标在游戏层单独维护，高度0.55 m，仅跟随玩家平移，环绕角度由CameraRig控制，不继承机器人转身或机械节点摆动。
5. **接入规则与时序。** 由GameSession提交规则结果，DOTween驱动游戏外层与箱子的共同位移进度，Blender剪辑只控制内部机械动作。Push仍为0.60 s，接触/释放位于0.10/0.50 s。滑行尾段、取消、暂停与快照恢复按第4、8节执行。
6. **完成游戏级验收。** 在实际关卡中验证四方向转身/移动/推动、0.01 m接触容差、滑行时玩家停留、表情锚点、双视角、动作中撤销和重开。记录在游戏测试/交付材料中；全部通过后才能标记主角游戏接入完成。

`Tools > Robot > Import and Validate` 会配置/重导入FBX，并写入材质、控制器、Robot.prefab、报告及预览，属于有副作用的资产流水线入口。常规接入时读取现成资产和报告；需要重新导入时先保护已有游戏包装和用户工作，执行后审查所有资源差异并重新验证哈希。新增游戏逻辑留在PlayerActor包装及项目脚本中，避免被流水线重新保存美术预制体时覆盖。

## 10. 白模、美术和反馈

以下保留表现目标；空间站套件已接入，基础音效已在 v0.7.0 独立分支接入（[音效说明](../Audio/Sfx.md)），气泡、BGM 等仍有未完成项，具体已实现范围见 [当前状态](../ImplementationProgress.md)。新增模型、材质角色、多路来源标识与资产验收以 [StationArtProduction.md](../Art/StationArtProduction.md) 为准。

- 色彩：墙/机身浅灰，底座深蓝灰，机器人识别色橙色；机关的连接色与来源插槽保持对应，断电时仍保留。供电状态使用独立灯光/图形，不覆盖连接身份；颜色同时辅以编号或符号。
- 多路输入的门分别显示各来源标识与供电状态，并说明Any/All；同一插槽控制多个门时身份一致。能源箱保持统一外观，不暗示同色配对。门的供电指示与实际开门状态分开，支持断电时的占据保护。

- 地板保留清晰格缝；LowFriction 用不同粗糙度、边框和连续纹理区别普通地面，即使关闭 Bloom 也能看懂。
- 目标插槽保留白色目标环与外围角标；只有被门引用的插槽显示插头，因此目标与门电源职责可组合。插头/目标旁不显示常驻文字。门按稳定 ID 排序分配颜色与图形，对应插槽的四边统一采用一个主关联色：优先该插槽为唯一来源的门，并列或无此门时按稳定门 ID 选择。多门的完整关系保留在按需线路及来源灯中，断电不褪去连接色。
- v0.7.1 移除受电门的浮动文字、底框与引线，各来源在门格边缘使用独立的空心/实心灯。开/关通行地标独立于供电；断电占据保开保留琥珀色十字。俯视指向门/插槽本体、第三人称靠近可见设备时显示对应分支，断电虚线、通电实线，平时收起线路。
- 白模门和箱子轮廓要能从第三人称识别；门上部在俯视模式隐藏时保留明确的通行标记。
- 气泡：推不动显示“!”或疑问符号，约 0.7 s；通关显示 ✓，约 1.2 s；只保留一个气泡，完成反馈优先。
- 气泡面向实际渲染相机，切换相机不消失，使用图形资源或确认支持的字体，避免依赖系统彩色 emoji。
- 最低音效集合：移动、推动接触、箱子落位、通电/断电、受阻、完成、UI 点击。没有素材时可用简单合成占位音。
- 灯光采用一套 URP 基础照明、柔和阴影和少量 Bloom。先验证灰阶识别度，再增加发光效果。

| I06 | I05 的门改由另一个已通电插槽供电 | 箱子进入门格(6,3)后停止 |
| I07 | 箱子在轨道(3,3)，下一格(4,3)是墙，玩家(2,3)，输入E | 第一格就失败，箱子仍(3,3)，计数不变 |
| H01 | 供电变化后撤销 | 玩家、箱子、计数和门精确恢复 |
| H02 | 滑行完成或表现中途撤销 | 整段滑行一次回退，不出现半格 |
| W01 | 只有辅助插槽通电 | 不完成 |
| W02 | 所有目标插槽通电，辅助插槽空 | 完成 |
| L04–06 | 回放第5.6节对应的正式参考解法 | 所有指令合法，终点和计数一致 |

测试夹具必须补齐合法目标/箱子数量；上表变体只描述被改变的关键条件。终点比较采用带 ID 的状态快照；参考解法中仅要求占据的目标格集合，不强制哪个同类型箱子对应哪个目标。

### 11.3 PlayMode 与实际构建验收

- 在普通移动、推板伸出、箱子滑行三种阶段切换镜头，最终逻辑状态与不切换一致。
- 第三人称环绕 360°，四方向输入映射正确；长按中环绕不突然改变方向。
- 俯视为真正正交投影，北方固定；19×9 等尺寸的作者测试图初次切换可完整显示。
- 推箱时机器人推板与箱子接触偏差 ≤0.01 m；撤销/重开无残留伸出姿态。
- 暂停、切关、重开和撤销后，不触发旧音效/旧完成弹窗或旧移动回调。
- 主菜单→三关→最终结算、选关、重玩、退出完整可操作。
- 打包后通关、退出、重启，已完成关卡和设置能恢复。
- 记录实际测试硬件；白模目标为 1920×1080、60 fps。目标性能不是未经测量的承诺。
- 查看 Console，无未处理异常、缺失脚本、材质错误或持续刷屏日志。
- 关闭附加音效与光效后，三关解法结果、计数、撤销和编辑器完整流程保持一致；门/插槽仍正确显示稳定状态。
- 在Push的0.05 s、0.30 s及滑行尾段分别执行Z/R，等待超过全部原反馈时长，不能再出现旧移动、旧门状态、重复结算或遗留气泡。
- 调整DOTween表现时长、音效与光效强度或Cinemachine镜头参数后，逻辑终点和参考解法不改变。
- 连续试玩/返回编辑器至少10次，无残留音源、粒子、活动会话Tween或被改写的作者数据；暂停时游戏反馈停止，菜单仍能操作。

### 11.4 Take-home：评审者操作脚本

目标是评审者阅读简短说明后，约10分钟能完成以下流程；时间为易用性目标，实际耗时在验收时记录。本流程只使用 Unity 界面，不修改源码、JSON，也不调用 Agent/MCP。

这是最终用户的操作路径。Agent 可通过实际界面的鼠标键盘或等价输入自动化自行完成同一路径的功能验收，并继续修复失败；直接调用业务API不能代替界面验证。独立评审者的易用性反馈另行记录，不作为每轮实现、测试和本地提交的前置审批，也不能把Agent操作记录冒充为独立用户评审。

| 步骤 | 评审操作 | 预期结果 |
|---|---|---|
| 1 | 用2022.3.51f1打开工程，按README进入 `Sokoban_Tools > Level Editor` | 无编译错误，能找到帮助、示例关卡和新建按钮 |
| 2 | 新建9×7地图，点击“一键生成边界墙”，核对自动生成的关卡 ID | 网格尺寸和落格预览正确，生成新的关卡ID |
| 3 | 放玩家(1,3)、箱子(2,3)、目标插槽(6,3)、门(7,3) | 所有元素能选中和修改；门显示缺少供电来源的提示 |
| 4 | 将(3,3)、(4,3)、(5,3)刷为低摩擦轨道，门设置Any并选择(6,3)的目标插槽为来源 | 轨道区别于普通地板，插槽到门有连接可视化，校验通过 |

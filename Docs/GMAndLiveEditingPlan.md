# GM 与关卡编辑器现场试玩迭代方案

日期：2026-09-16。状态：M1–M3 主要能力已实现，M4 留待后续。本文保留行为契约、分期和验收要求；具体操作见 [LevelEditorGuide.md](LevelEditorGuide.md)，已执行验证及其边界见 [ImplementationProgress.md](ImplementationProgress.md)。

同日补充：按 Energy（能源箱）/Cargo（普通箱）机制实施。普通箱共享推动、滑行和占门保护，但不供电、无需归位；当前正式目录为 L01–L06。规则依据见 [GameDesign.md](GameDesign.md)，箱型、旧版哈希和录制有效性纳入本轮实现与回归。

目标：开发者能在运行中检查问题、可撤销地调整玩家和箱子位置，并把当前局面交给现有关卡编辑器，修改后继续试玩。

## 1. 本次决定与范围

- GM 采用“命令入口、专项状态页、场景显示”结构，借鉴 Element_Ballance 的分类、搜索、参数配置与可调整面板布局。
- **GM 移位支持撤销。** 本决定替代讨论早期“GM 默认不可撤销、清空历史”的候选方案。普通移动与 GM 移位共用玩法撤销历史。
- GM 可直接放置玩家和现有箱子，无需满足路径可达、相邻移动和正常推动条件；提交后的局面仍需满足运行时数据约束。
- 箱子增删、箱型变更、地形、机关连接等定义编辑以现有关卡编辑器为主要入口。GM 提供进入现场编辑的快捷入口；简易增删箱子按钮在结构编辑能力完成后复用同一应用流程，并明确指定 Energy 或 Cargo。
- 现场编辑支持在 Unity Play Mode 内“捕获局面 → 编辑临时草稿 → 应用并继续试玩”，无需为每次改图退出 Play Mode。
- 运行时 GM 面向 Editor 与 Development Build；完整现场关卡编辑器仅在 Unity Editor 内提供。首版不把完整画笔、文件管理界面做进独立程序。
- 结构修改采用“新试玩起点 + 重建棋盘”。编辑器撤销与玩法撤销分开；暂不支持一次 Z 跨越不同关卡结构的应用边界。
- 本迭代是开发工具扩展，不引入玩家可用的传送、造箱、改地形玩法，也不替代 GDD 原有编辑器交付要求。

下文“结构编辑”包含箱型等关卡定义变更，即使实体 ID、数量与坐标没有变化。普通 GM 移位保持箱型不变；改箱型沿用结构应用边界。

运行时 GM 沿用 KToolkit + UGUI；Unity 关卡编辑器沿用 UI Toolkit 与 SceneView。保持 Unity 2022.3.51f1、URP 14、Cinemachine 2.x 及现有资产接口。

## 2. 当前基础与需要补齐的部分

| 当前实现 | 可复用部分 | 本轮增量 |
|---|---|---|
| GameSession | 不可变 GameState、快照撤销、方向序列 | 历史同时保存指令与录制有效性，增加 GM 状态提交入口 |
| RuleEngine | 两类箱子的占格、能源箱供电、门占据保护、完成判定 | 共享状态构造与运行局面校验；结构或箱型编辑时建立新规则实例，刷新能源箱 ID 集合 |
| LevelRunner / CommandPresenter | 动作取消、输入清理、关卡装载、状态通知 | GM 提交编排、调试输入占用、现场会话身份与事务式应用 |
| BoardView | 从 Session 恢复玩家、箱子和供电表现 | 同结构修改直接恢复；结构修改创建新棋盘并清理旧资源 |
| LevelDocument / LevelEditorWindow | 两类箱子画笔、箱型属性、编辑撤销、校验、草稿及 v1/v2 数据兼容 | 独立现场草稿与当前局面覆盖显示；受控开放 Play Mode 编辑，保留类型与版本 |
| PlaytestBridge | 作者副本试玩、场景恢复、参考解法收集 | 当前局面捕获、现场会话关联、应用新起点、退出与重载恢复 |
| SolutionRecord | 原始关卡起点的方向序列验证 | GM 有效性门禁；与调试快照/调试回放区分 |

迭代前的窗口在 Play Mode 中禁用编辑，PlaytestBridge.Play 拒绝在 Play Mode 中重新进入试玩。现通过 LiveEditWorkspace 和窗口现场模式提供独立入口，普通作者文档在游戏运行中仍受保护。

当前 RuleEngine 复制 LevelDefinition，BoardView 按定义创建实体；因此只改 Transform、只改作者数组，或只替换 GameState 都不足以完成结构编辑。

## 3. GM 首版体验

默认入口为 F1。工作台顶部为搜索和常用操作，中间为分类页，底部显示执行结果。使用中文文案，延续现有简约 UGUI 风格，并支持字号与面板宽度调整。

| 页面 | 首版功能 |
|---|---|
| 关卡 | 查看关卡 ID、内容哈希和会话类型；重开；在允许导航的会话中选关；Editor 内打开“现场编辑当前局面” |
| 局面 | 选择玩家/箱子，显示箱子 ID、类型与坐标，分别统计能源箱/普通箱数量；输入坐标或点选格子；移动、修改玩家朝向、交换两个占格对象；撤销最近操作 |
| 机关 | 分别显示插槽占据者 ID/类型与是否通电；门的 Any/All 条件与来源、通电状态和实际开闭原因；高亮关联对象 |
| 诊断 | 最近操作及失败原因、玩法输入被阻止的原因、动画忙碌状态；复制当前诊断记录 |

首版场景显示包含网格坐标、实体 ID 与箱型、插槽到门的连接。显示开关不进入玩法撤销历史。普通箱压住插槽时显示“已占据，未供电：普通箱不供电”；普通箱撑住断电门时显示“未通电，占据保护打开”，不把开门误报为供电成功。

- GM 工作台操作时占用游戏输入并释放鼠标；输入框、拖动面板、点选格子不触发移动、Z/R、镜头旋转或底层按钮。
- 只读监视条可以保持显示并允许继续游戏。输入占用、游戏暂停、动画暂停分别管理；打开 GM 不依赖打开正式 PausePage。
- Esc 优先关闭点选/参数子界面，再关闭 GM；由单一入口消费，不能同一按键继续触发正式暂停菜单。
- 关闭面板恢复之前的有效暂停/鼠标状态，清空长按缓存，按键释放后才接受新移动。
- 转场、会话销毁或现场应用期间拒绝冲突操作，并显示原因。正式试玩的导航隔离规则继续生效。
- 诊断信息区分已提交的逻辑局面与正在播放的表现进度；细化到 Microstep 的逐步播放留到后续增强。

## 4. GM 移位与撤销契约

### 4.1 允许跳过的移动规则

GM 放置可跨越墙壁和关闭的门、跨任意距离，不执行沿途推动或滑行。箱子放到低摩擦格时停在指定格；下一次正常推动再使用低摩擦规则。

候选状态必须满足：

- 坐标为地图内的整数格，落点是 Floor 或 LowFriction；不允许落在 Wall/Void。
- 一个玩家；现有箱子 ID 集合及 ID 对应的 Energy/Cargo 类型保持不变，ID 可解析；玩家与箱子、箱子之间不重叠。交换能源箱与普通箱只交换位置，不交换 ID 或类型。
- 玩家朝向有效。箱子没有独立的玩法朝向字段，首版不增加这一概念。
- 门格可被玩家/箱子占据，提交后使用现有占据保护计算开闭。
- 批量移动、交换位置按最终候选局面校验，整体成功或整体不改变。

允许在已完成局面中使用 GM；修改后按能源箱占据目标插槽重新计算供电和完成状态并同步结算 UI。普通箱占目标格不计完成，所有目标通电时也不要求普通箱归位或保持可移动。无效操作与没有实际变化的操作不进入历史。

### 4.2 统一历史条目

历史条目至少保存操作前的 GameState、Commands 和参考解法录制有效性；可附操作类型及显示名称。GM 不追加 N/E/S/W 字符，也不增加或清零已有移动/推动次数。

Undo 已从每次截去一个方向字符改为恢复完整历史条目。普通移动与 GM 修改都保存相同的快照信息。

示例：普通移动 A → GM 移位 B → 普通移动 C，三次撤销依次恢复 C 前、B 前、A 前。一次批量 GM 修改只占一个历史条目。首版运行时只要求 Undo，不新增 Redo；编辑器保留现有 Undo/Redo。

完成真实 GM 修改后，参考解法录制标记为无效。撤销回该修改之前时，原 Commands 和有效性一起恢复；当前仍包含其他 GM 修改时继续保持无效。

普通重开恢复本会话起点并清空玩法历史。对于原始关卡起点，可恢复正常录制；对于现场捕获起点，仍属于调试试玩，不能因重开自动获得原关卡参考解法资格。

### 4.3 提交顺序

1. 核对活动会话和版本；复制已提交的逻辑状态，生成并校验候选局面。失败不取消旧动画，不改变历史。
2. 成功提交时取消旧动作、自动回放和过期回调，清理输入缓存。
3. 保存完整历史条目，提交新 GameState，更新录制有效性。
4. 根据新状态计算供电与完成状态，调用 BoardView 恢复位置、姿态和机关，刷新 LevelRunner 镜像状态、消息及 UI。
5. 保持当前视角及有效暂停状态；玩家瞬移时重置必要的相机跟随缓存，避免镜头沿旧轨迹追赶。

当前动画播放时逻辑已经提交完整动作，因此 GM 与现场捕获统一以已提交的稳定局面为准。取消演出后对齐该局面，不从半格 Transform 反推棋盘状态。

### 4.4 箱型变更的边界

当前 [CrateDefinition.kind](../Assets/Scripts/Gameplay/Domain/LevelDefinition.cs) 属于关卡定义，GameState 仅保存箱子 ID 到格子的映射；[RuleEngine](../Assets/Scripts/Gameplay/Domain/RuleEngine.cs) 初始化时复制定义并缓存 energyCrateIds。因此：

- M1 的两类箱子移位继续共用快照撤销，固定定义内无需为每次移动重复保存箱型。
- Energy ↔ Cargo 归 M3 现场草稿编辑。编辑撤销同时恢复类型与必要的 schemaVersion 变化；应用时创建新规则实例、重建对应外观并重算供电、门与完成状态，建立新的试玩起点。
- 改箱型不生成新实体 ID，也不隐式移动箱子。即使只改类型、所有坐标相同，也必须刷新逻辑与表现，不能只改材质或直接修改被旧规则忽略的作者字段。
- 首版不提供可由游戏 Z 跨越的箱型修改。若以后需要，再扩展包含定义版本的运行时历史，不能把类型变化混入仅保存 GameState 的移位历史。

## 5. 现场编辑并继续试玩

### 5.1 工作副本与会话

同时区分以下数据：

| 数据 | 作用与保存方式 |
|---|---|
| 原作者文档 | 原文件路径、未保存修改、参考解法、保存基线；进入现场编辑不覆盖它 |
| 进入现场前的运行快照 | 关卡定义、逻辑状态、玩法历史/指令/录制资格、原会话身份、暂停及相机设置；用于返回 |
| 现场草稿 | 独立定义副本（含 schemaVersion 和每个箱子 ID 对应的 kind）、玩家/箱子当前摆放、来源哈希、草稿版本；拥有自己的编辑 Undo/Redo 和备份 |
| 已应用试玩起点 | 最近一次通过校验并成功应用的定义与起点状态；R 回到这里，计数从零开始 |

现场草稿以“临时现场草稿”明确标识，使用独立备份路径与会话 ID，不复用作者的 Current.json，也不自动复制或覆盖正式关卡文件。

捕获、复制、序列化、恢复、另存和结束现场试玩均按箱子 ID 关联类型与位置；不通过位置、外观或数组顺序猜测箱型，也不只保存一组无类型坐标。正常推动和交换位置不会改变这种关联。

### 5.2 操作流程

1. 在 GM 或关卡编辑器点击“现场编辑当前局面”。主菜单无局面、转场中或目标会话已失效时显示不可用原因。
2. 捕获稳定局面，取消旧演出并对齐显示；占用试玩输入，保留原暂停状态。打开现有编辑器的现场草稿模式，原作者文档继续保留。
3. 复用现有二维棋盘、SceneView、画笔和属性区；以当前局面显示玩家/箱子。草稿允许暂时无效，修改不逐笔影响正在运行的棋盘。
4. 点击“应用并继续试玩”。验证草稿、活动会话及来源版本；准备新规则、状态和隐藏的表现对象。
5. 准备全部成功后切换到新起点，清理旧对象/材质/Tween，玩法历史与计数清零，退出编辑输入占用并继续试玩。应用失败则保留旧可玩局面和草稿，显示可定位错误。
6. 可再次进入现场编辑，捕获当前试玩位置形成下一版草稿；尚有未应用编辑时提供“继续编辑现有草稿”或明确的“重新捕获并替换”，不得静默丢弃修改。
7. “结束现场试玩”恢复进入现场前的稳定局面、玩法历史、录制资格和原会话身份。原作者文档的脏状态与保存基线不改变；现场草稿可继续保留。

成功应用后的会话显式标记为现场试玩，不能仅依赖启动时的 IsPlaytest 值推断。CampaignIndex、正式下一关/选关入口与未来进度写入按现场会话处理，不把临时修改混入正式流程。

应用属于完整替换操作：先准备后切换，失败不留半套棋盘。LevelRunner.InstallSession 已将规则与隐藏表现对象准备放在旧表现清理之前；验证和准备失败时保留旧局面。

### 5.3 两类撤销与重开

| 操作 | 撤销/重开的范围 |
|---|---|
| 游戏中 Z / GM 撤销按钮 | 当前已应用起点之后的普通移动与 GM 移位 |
| 编辑器 Ctrl+Z / Ctrl+Y | 当前现场草稿的编辑；不会自动改动活动游戏 |
| 编辑器撤销后再次应用 | 创建另一个试玩起点，清空该起点之前的玩法历史 |
| 现场试玩中 R | 恢复最近成功应用的试玩起点 |
| 结束现场试玩 | 恢复首次进入现场编辑前的运行快照 |

箱子增删、箱型变更和地形修改的撤销由编辑历史承担。GM 的快捷增删入口也遵守此应用边界，在界面上说明“将建立新的试玩起点”；它们不伪装为可由游戏 Z 跨结构撤销的移位命令。

## 6. 运行局面与作者关卡的校验边界

现场捕获不能简单地把当前位置填回 playerSpawn 后直接当作正式关卡：当前 LevelValidator 禁止玩家出生在门上，但正常运行允许玩家站在门格；当前正式校验要求能源箱数量不少于目标数，普通箱不计入供电能力。

实现需要分别表达：

- **结构约束**：地图尺寸和地形格式、实体 ID、箱型与数据版本、机关类型、供电引用及机关所在层合法。
- **运行局面约束**：玩家/两类箱子有效占格、箱子 ID 与结构集合及类型映射对应、朝向合法；允许玩家或任一箱型占据门格。
- **作者起点要求**：现有出生点限制、能源箱数量要求及正式关卡校验。用于目录接入、标准试玩，以及现场草稿转换为可试玩关卡的校验；普通作者文档仍可保存待修复的草稿。

现场快照由“定义副本 + 独立起点状态”组成；规则初始化必须明确选择正式关卡或现场快照入口，避免反射修改私有字段，也避免为支持现场编辑全局放宽正式校验。现场 UI 的玩家/箱子位置以起点状态为准，现有作者编辑操作通过适配更新草稿。

现场增删箱子仍要求唯一 ID、合法类型与落点、一个玩家及至少一个目标。能源箱少于目标数可在明确标识的现场模式中作为警告，供测试无解局面；正式关卡保持原错误级别。增加普通箱不能消除能源不足警告，Energy 改为 Cargo 也可能触发该警告。删除供电来源造成悬空引用、把对象留在墙/虚空中等错误必须修复后才能应用。

普通箱停入不再需要的死角可能是正确解法。诊断提示须区分箱型，不能以“所有箱子都能继续移动/必须归位”作为应用或通关条件；静态提示不宣称整关有解或无解。

地形擦除继续使用现有规则处理受影响实体与机关连接；新增/删除实体时同时更新现场状态中的 ID 集合。把当前摆放另存为关卡时，显式转换为作者起点并执行完整校验；不合法则定位问题，不能自动挪走玩家或伪造合法出生点。

## 7. 保存、录制与生命周期

- “应用试玩”只更新运行会话及现场备份；Ctrl+S 在现场模式保存现场草稿，不覆盖原关卡。
- “另存为关卡副本”沿用新 ID 与独立路径；“将修改带回作者文档”是明确操作，把转换后的候选数据作为一次作者编辑，不自动写入磁盘。界面需要区分这两种行为与保存现场草稿。
- 带回作者文档前核对捕获时的文档身份与版本；原文档已另行修改或已切换时保留双方内容，允许另存副本，不静默覆盖新的作者工作。
- 原参考解法不能自动沿用现场位置或新结构。来源哈希变化后保持过期状态，只有从对应作者起点重新验证成功才可建立新证明。
- 原始起点且无残留 GM 修改的会话继续使用 SolutionRecord。现场起点的回放应另存为“起点快照 + 定义哈希 + 后续方向序列 + 期望终点”的调试记录，不冒充正式参考解法。
- 第一阶段诊断导出记录会话类型、关卡/起点标识、逻辑局面、最后操作/拒绝原因、录制资格和表现状态。操作日志与可执行方向序列分开。
- 现场录制/草稿关联采用会话 ID、草稿版本和起点内容标识，避免只用原关卡 ID 就把旧录制收回作者文档。
- 原作者草稿与现场草稿分别备份。关闭窗口、退出 Play Mode 或域重载后保留可恢复草稿；不承诺跨重载保留 Unity 编辑撤销栈。
- 窗口关闭须解除本工具持有的输入占用，并保留未应用草稿。脚本重载后重新核对活动实例；不能可靠恢复运行会话时回到可恢复草稿状态，不自动把旧草稿应用到另一个关卡。
- 退出 Play Mode 仍通过现有桥接恢复原场景；现场数据不得由 CollectRecording 自动并入原作者文档。所有事件订阅、输入占用和运行对象都需清理。

箱型与版本兼容遵守现有 [LevelJson](../Assets/Scripts/Gameplay/LevelFlow/LevelJson.cs) 和 [LevelDocument](../Assets/Scripts/Editor/LevelEditor/LevelDocument.cs) 约定：

- 未修改的 v1 关卡按全 Energy 读取，保持 v1 字段布局与原内容哈希；仅打开 GM、捕获或复制不能自动升级来源定义、使旧参考解法过期。
- v1 草稿新增 Cargo 或把现有箱子改为 Cargo 时，箱型与 schemaVersion=2 在同一次编辑内提交、撤销。v2 的每个箱子显式保存 kind；未知类型、v2 缺失 kind、v1 文件夹带 kind 等继续拒绝。
- 删除最后一个 Cargo 或手动改回 Energy 不自动降回 v1；撤销当初的升级操作可以精确恢复原版本。已有新图默认 v2 的行为保持一致。
- 类型变化参与定义哈希，即使全部位置相同也会使旧解法证明过期；不能只刷新哈希就宣称重新验证成功。
- 新的调试快照/回放终点按 ID、kind、Cell 校验，并绑定定义与起点内容；两类箱子交换后整体占格集合相同，不等于状态相同。现有 SolutionRecord 的无类型 expectedCrateCells 不能单独用作现场状态恢复判据；原格式仍通过绑定的关卡定义和完整规则回放维持兼容，本轮不要求迁移全部旧解法。

## 8. 代码与资源安排

以下接口名称为建议，可按实现需要调整；职责边界保持稳定。

| 位置 | 职责 |
|---|---|
| Assets/Scripts/Gameplay/Domain/ | 扩展历史条目；候选状态校验/构造；现场快照初始化契约；保持纯 C# |
| Assets/Scripts/Gameplay/Debug/ | GM 操作与活动会话编排、调试记录；需要 Unity API 的运行时适配 |
| Assets/Scripts/UI/GM/ | GmPage、状态页、坐标选择、输入占用；只提交操作与显示结果 |
| Assets/Scripts/Presentation/ | 调试叠加显示、状态恢复、结构重建及相机瞬移同步 |
| Assets/Scripts/Editor/LevelEditor/ | 现场草稿、现有画笔适配、应用/返回流程、保存与 PlaytestBridge 扩展 |
| Assets/Resources/UI_prefabs/screens/GM/ | KToolkit GM 页面资源，遵守已有资源加载约定 |
| Assets/Scripts/Tests/EditMode/、PlayMode/ | 规则/历史/草稿测试与实际运行集成测试 |

优先提供少量明确入口，例如 TryApplyDebugEdit、CaptureLiveSnapshot、ApplyLiveDraft；首版不要求通用反射命令系统或给每条操作编写反向命令。

Runtime 不引用 UnityEditor；Editor 层依赖 Runtime 与 Domain。GM 快捷增删需要共享的纯数据编辑能力时，按实际需要从作者工具抽出对应操作，不复制一套规则，也不重写全部编辑器框架。

GM 入口与类型按 Editor/Development Build 范围启用，Editor 桥接另行隔离。Resources 不会因代码条件编译自动剔除，构建必须检查调试资源引用与缺失脚本；正式非开发构建无可触发的 GM 入口。完整编辑器不进入 Player。

## 9. 分期交付

各阶段可以独立实现、验证和提交。M1–M3 构成本次计划的主要交付；M4 为后续增强，不阻塞现场编辑闭环。

| 阶段 | 范围 | 完成门槛 |
|---|---|---|
| M1：可撤销 GM | 分类/搜索入口、箱型与占据/供电状态、两类箱子坐标/点选移位、朝向/交换、统一历史、诊断导出、输入与录制门禁 | 普通操作与 GM 混合撤销保留 ID/箱型，动画中使用无残留，Editor 与开发构建可操作 |
| M2：捕获现场并继续试玩 | 独立现场草稿、类型与版本保留、同实体/同箱型/同地形的位置编辑与应用、原文档保护、结束现场试玩与生命周期恢复 | 不退出 Play Mode 完成捕获→编辑位置→应用→继续→返回，原作者内容与两类箱子的原运行快照可恢复 |
| M3：结构编辑闭环 | 复用箱子增删与类型属性、地形画笔、机关与地图尺寸编辑；校验分层、事务式重建、版本升级与编辑撤销、新起点、另存/带回作者文档 | 修改数量/箱型/地形后立即继续，规则缓存与外观一致，失败保持旧局面；Editor GM 增删快捷入口明确箱型并复用同一流程 |
| M4：后续增强 | 参考解法可视回放、动画速度与 Microstep 检查、调试快照回放、更多监视项；按实际需求扩展开发包内的结构修改入口 | 在已有闭环上独立验收，不把这些能力误标为 M1 已有 |

M1 开始就采用完整历史条目，避免后补 GM 撤销；M2 开始就分离作者起点与运行快照校验，覆盖玩家站门格和普通箱占插槽的捕获。M3 不引入跨结构或箱型变更的游戏 Z 撤销。

## 10. 验收矩阵

| 编号 | 场景 | 预期 |
|---|---|---|
| GM01 | 普通移动→GM 移位→普通移动→连续撤销 | 每次状态、计数、Commands、录制资格精确恢复 |
| GM02 | 批量交换、无效落点、重复放到原格 | 交换一次撤销；失败/无变化无历史与动画副作用 |
| GM03 | 推动起步、接触、滑行途中 GM 与撤销 | 采用逻辑终点，不出现半格、旧回调或旧通关弹窗 |
| GM04 | 移走插槽箱子、站在未通电门格、撤销 | 供电、占据保护、模型与碰撞体一致 |
| GM05 | GM 达成全部目标后，再撤销或移走箱子 | 完成状态和结算 UI 正确进入/退出 |
| GM06 | 打字、选格、关面板、按住方向键、Esc | 无输入穿透；旧按键释放后才能移动；暂停状态正确 |
| GM07 | GM 修改后保存参考解法、撤销全部修改后再录制 | 前者拒绝并说明原因；后者可从原起点验证 |
| GM08 | 开发构建及非开发构建 | 前者 GM 可用；后者入口不可触发；均无缺失脚本和 Editor 依赖 |
| GM09 | GM 把 Cargo 放到目标/辅助插槽或断电门格，再撤销 | 插槽不供电、不误判完成；门仅因占据保持打开；撤销恢复全部派生状态 |
| GM10 | Energy/Cargo 交换位置、连续移动与撤销；Cargo 留在死角通关 | 类型绑定 ID，坐标集合相同也按 ID 校验；完成只要求目标由 Energy 供电 |
| LIVE01 | 作者有未保存修改时捕获现场 | 原文档、路径、解法、脏状态与备份不被覆盖 |
| LIVE02 | 玩家正在门格、箱子在轨道上时捕获 | 合法运行局面可继续；不错误套用作者出生限制 |
| LIVE03 | 编辑草稿未应用、应用失败 | 活动局面与玩法历史不变；草稿保留且错误可定位 |
| LIVE04 | 新棋盘准备过程失败 | 无半套新棋盘、无泄漏，旧局面仍可恢复/继续 |
| LIVE05 | 增删两类箱子、总箱数足够但能源不足、修改地形和门来源 | ID/类型/占格/引用一致；能源数量的现场警告与正式错误按规则区分 |
| LIVE06 | 结构应用后按 Z、R；编辑 Ctrl+Z 后再应用 | Z 不跨应用边界；R 回新起点；编辑撤销仅改变草稿 |
| LIVE07 | 从正式关卡或作者试玩进入，再结束现场试玩 | 原身份、稳定局面、历史、暂停与录制资格恢复 |
| LIVE08 | 保存草稿、另存副本、带回作者文档 | 三种动作边界明确；副本新 ID；未显式保存不覆盖原文件 |
| LIVE09 | 新结构/新起点产生录制，退出后收集 | 不误收为原关卡参考解法，过期哈希不伪造为已验证 |
| LIVE10 | 草稿关联期间换关、关闭窗口、退出 Play、域重载 | 不应用到错误会话；草稿可恢复，输入占用与订阅释放 |
| LIVE11 | 实际 UI 连续捕获/应用/返回至少 10 次 | 无重复相机、角色、棋盘、Tween、材质和事件监听残留 |
| LIVE12 | 插槽上的 Energy 改 Cargo 再应用，编辑撤销后再次应用；反向转换 | 能源 ID 缓存、供电、门、完成状态与箱体外观一起更新，类型变更不修改 ID |
| LIVE13 | v1 捕获、复制；新增/转换 Cargo→编辑撤销；v2 备份/重载/另存/返回 | 未修改 v1 哈希保留；升级与撤销完整；按 ID 恢复类型，不自动降级或把 Cargo 默认为 Energy |
| LIVE14 | 未知箱型、v2 缺失 kind、v1 含 kind；仅改箱型后验证旧录制 | 非法数据阻止应用，旧局面保留；箱型改变使哈希失效，恢复判据包含 ID/类型 |
| REG01 | 原编辑器试玩往返、L01–L06 解法与现有 UI 流程 | 原有两类箱子规则、录制、v1/v2 数据、场景恢复与六关导航测试继续通过 |

规则、历史和数据校验优先 EditMode；输入、动画、界面、重建及生命周期使用 PlayMode。M1 验证开发/非开发构建，M3 完成后再次检查 Player 隔离。实机连接与编译流程见 [UnityMcp.md](UnityMcp.md)，各阶段只运行受影响的验证。

界面验收覆盖“移位→撤销”和“现场编辑→改箱子/地形→应用→继续→保存副本”。Agent 可自行操作实际窗口/Game View，或通过等价输入自动化验证并记录结果；只调用业务API不代表界面路径通过。发现问题继续修复与复验，无需等用户逐步确认。独立用户评审作为另一类证据记录。

上述矩阵是验收目标，不等于每一条都已逐项独立验收。当前测试、实际界面操作、域重载恢复与构建证据汇总在 ImplementationProgress 和 Validation/GMAndLiveEditingResults.json；未覆盖范围在那里单独列出。

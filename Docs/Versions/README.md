# 开发版本台账

从本次文档整理开始，为后续实现迭代建立可追踪的开发版本。版本号用于关联需求、计划、验收与 Git 提交；历史 01–07 阶段保持原编号，文档修订号、资产协议和关卡数据版本各自独立。

## 编号规则

使用 `v主版本.次版本.修订号`，按已登记的最高编号顺序规划，不复用已有版本号：

- `v0.1.0`：本轮文档分类与版本追踪基线。
- 新功能、新玩法或独立功能迭代：增加次版本，修订号归零，例如 `v0.2.0`。
- 修复、局部重构、文档或配置维护：增加修订号，例如 `v0.1.1`。
- 进入 `v1.0.0` 必须明确规划正式交付范围并完成相应验收；后续不兼容变更增加主版本。`v0.x` 阶段的不兼容变更增加次版本，并在计划中写明兼容影响和迁移办法。

未立项的“下一版本”不提前占号。多人或多个任务并行时先核对台账，登记独立范围与不同编号；同一目标的后续修正继续使用已有进行中版本。

## 执行方式

1. **开始实现前**：在台账登记版本，新增 `Docs/Versions/V主版本.次版本.修订号.md`。写明起始提交、目标、范围、不包含项、验收方式及已知依赖，状态为“已规划”。编号和常规规划可自主完成。
2. **开始与调整**：开工时改为“进行中”；需求澄清或同目标修复更新该计划。独立追加需求另行规划，不把已完成版本改写成新范围。
3. **验证与提交**：记录实际检查、失败与修复、剩余限制，并同步台账。通过约定检查后标为“已完成”；受阻时记录证据及下一步，不能标为通过。
4. **关联提交**：该版本的聚焦提交使用 `[vX.Y.Z]` 前缀，例如 `[v0.2.0] feat: ...`。最终回复给出版本号、验证结果和提交哈希。可用 `git log --oneline --fixed-strings --grep='[v0.2.0]'` 查询全部相关提交；计划与提交同批保存，无需为写入自身哈希再追加提交。

每份版本计划使用“目标与范围 / 验收计划 / 执行结果与限制”三部分即可。文件中的状态可用：已规划、进行中、受阻、已完成、已取消。版本登记不创建 Git 标签、不变更 PlayerSettings 版本、不自动发布。

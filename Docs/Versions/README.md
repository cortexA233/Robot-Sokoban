# 开发版本台账

从本次文档整理开始，为后续实现迭代建立可追踪的开发版本。版本号用于关联需求、计划、验收与 Git 提交；历史 01–07 阶段保持原编号，文档修订号、资产协议和关卡数据版本各自独立。

后续需求、版本分工、执行顺序、方案风险与待细化项统一维护在 [迭代路线图](Roadmap.md)。按用户要求，现已将 R01–R09 排入 v0.4.0–v0.9.0 六个正式计划。v0.4.0、v0.5.0 已完成，v0.7.0 音效子项按用户要求提前实施；其余未启动范围保持原规划，开工时直接使用对应版本，不再重新分配。版本规划本身不代表开始实现。

## 编号规则

使用 `v主版本.次版本.修订号`；已登记版本的编号与范围可追踪，不复用已完成或已取消的编号：

- `v0.1.0`：本轮文档分类与版本追踪基线。
- 新功能、新玩法、独立体验迭代或完整交付里程碑：在最高已登记次版本之后分配下一次版本，修订号归零，例如 `v0.4.0`。批量排期按执行顺序连续登记。
- 针对已实现基线的修复、局部重构、文档或配置维护：使用该基线主/次版本下下一未使用的修订号，例如 `v0.3.3`。尚未实施的未来次版本不抬高维护版本的基线；进行中版本内同目标修正不另起修订号。
- 进入 `v1.0.0` 必须明确规划正式交付范围并完成相应验收；后续不兼容变更增加主版本。`v0.x` 阶段的不兼容变更增加次版本，并在计划中写明兼容影响和迁移办法。

明确要求排期的工作现在就分配版本，并写出可执行范围、依赖和验收；只有未纳入排期的候选想法暂不占号。已规划版本按路线图执行，即使台账已有更高的未来编号也不跳号。多人或多个任务并行时先核对台账；同一目标的后续修正继续使用已有进行中版本。

已规划但未开工的版本可以调整范围与顺序，须同步本台账、路线图和对应计划；取消则保留记录，完成后不改写历史范围。新增工作不要隐含改变已登记版本的含义。

## 执行方式

1. **规划时**：在台账登记版本，新增 `Docs/Versions/V主版本.次版本.修订号.md`。写明策划基线、目标、范围、不包含项、验收方式及前置版本，状态为“已规划”；远期版本的实施起始提交标为待记录，不编造未来提交。
2. **开始与调整**：先选中排期里已有版本，核对前置条件、细化尚待讨论的方案、记录当时真实实施起始提交，再改为“进行中”；需求澄清或同目标修复更新该计划。独立追加需求另行规划，不把已完成版本改写成新范围。
3. **验证与提交**：记录实际检查、失败与修复、剩余限制，并同步台账。通过约定检查后标为“已完成”；受阻时记录证据及下一步，不能标为通过。
4. **关联提交**：该版本的聚焦提交使用 `[vX.Y.Z]` 前缀，例如 `[v0.2.0] feat: ...`。最终回复给出版本号、验证结果和提交哈希。可用 `git log --oneline --fixed-strings --grep='[v0.2.0]'` 查询全部相关提交；计划与提交同批保存，无需为写入自身哈希再追加提交。

每份版本计划使用“目标与范围 / 验收计划 / 执行结果与限制”三部分即可。文件中的状态可用：已规划、进行中、受阻、已完成、已取消。版本登记不创建 Git 标签、不变更 PlayerSettings 版本、不自动发布。

v0.4.0–v0.9.0 的初始计划随 `[v0.3.3]` 文档提交保存；各版本自己的提交检索用于后续实施记录。v0.5.0 已完成，下一执行版本为 **v0.6.0**；按用户要求，v0.7.0 音效子项在独立分支提前实施。

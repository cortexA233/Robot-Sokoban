# 后续迭代路线图

更新：2026-09-17 · 规划基线：`cc2ee0e` / 玩法 v0.3.0 已封版 · 本次文档版本：[v0.3.2](V0.3.2.md)。

这份路线图收纳用户已提出的方向和建议补充项，供后续讨论与排期。**列入规划不等于开始实现，也不代表方案已定。** 当前实现与缺口见 [实现状态](../ImplementationProgress.md)，实际立项与验收见 [版本台账](README.md)。本次只读核对文档与代码，没有重新试玩或验证美术效果。

## 立项与版本约定

- 后续开启的每个独立迭代，都先核对版本台账、选择下一未使用版本号并建立 `V主版本.次版本.修订号.md`，写清起始提交、范围、不包含项、依赖与验收；先“已规划”，开工前再改“进行中”。文档和配置维护也遵循该规则。
- R01–R09 是稳定的需求索引，**不是预占的版本号或固定执行顺序**。下面所有条目当前均未分配开发版本；方案待讨论时不创建空的正式版本。若台账没有新增记录，下一个独立功能迭代按规则可使用 v0.4.0，实际仍以立项时的最高编号为准。
- 正式立项时在本表补上版本计划链接。一个方向可以拆成多个可独立验收的版本；只有共同依赖且范围紧密时才合并。同一目标的澄清和修复留在活跃版本，已封版的 v0.3.0 不追加范围。
- 各版本完成后记录实际证据与限制，同步状态、检查差异并创建带 `[vX.Y.Z]` 的聚焦提交。实现、验证受阻和仅完成设计必须分别记录；不能把路线图条目写成已交付。
- 新的明确用户需求可以调整优先顺序；常规编号、计划整理、测试和本地提交自主执行。具体方案影响产品范围时再讨论，不把每一步实施都变成审批。

## 用户提出的四项迭代

### R01 · UI 文案简化与样式优化

**目标：** 缩短理解和操作路径，沿用项目现有简约方向进行适度美化。覆盖主菜单、HUD、选关、暂停、结算、设置；关卡编辑器文案归 R02，GM 是否纳入另定。

- 先列出“必须常显、按需查看、可删除”的信息，统一按钮动词和目标/插槽/供电/门的术语，再调整间距、字号、对齐、对比、按钮状态与视觉层级。
- HUD 优先保留目标进度、必要操作及关卡状态；长说明考虑放到按需帮助。简化时要保留“通电”与“开门”、“能源箱”与“普通箱”的差别。
- 现有第三人称锁定鼠标，俯视可点 HUD；新布局需要同时照顾快捷键和鼠标路径。Prefab 手工布局与重建工具的维护方式应在实现时统一，避免下一次生成覆盖新样式。
- **立项前待定：** 具体文案清单、视觉参考、HUD 信息量、帮助入口、涉及哪些页面；本规划不指定新风格稿或全站重做。
- **验收目标：** 逐页文案可追溯；720p/1080p 无遮挡或溢出；按钮常态/悬停/选中/禁用可识别；菜单→关卡→暂停→结算→下一关/选关、设置保存和快捷键流程保持可用。

依据：[UI 实现](../UI/UIImplementation.md)。

### R02 · 关卡编辑器易用性与分类

**目标：** 让作者更容易找到对象、理解属性并完成制作。当前顶栏混合文件、校验、试玩与配方操作，画笔按枚举逐项列出，适合重新整理。

- 菜单候选分组：文件、编辑、校验与试玩、目录、现场编辑、帮助；对象候选分组：地形、角色与箱子、机关，再细分能源箱/普通箱、目标插槽/辅助插槽、门/转向板。最终树形、折叠面板或标签形式待方案讨论。
- 用名称、图标或小预览解释对象用途；仅显示当前对象相关属性。擦除层、当前画笔、朝向、选中对象和未保存状态应持续明确。
- 分类深度以常用操作能否快速到达为准；类别变多不应让每次放置多走几层菜单。优先梳理现有逻辑种类；新增玩法对象或美术变体若进入范围，须另列其规则、资源与验收。
- **立项前待定：** 当前最费力的制作步骤、分类树、搜索/快捷入口的必要性、是否覆盖现场编辑面板。已有保存、撤销、草稿、录制能力是需要保护的基线。
- **验收目标：** 从空白图放置两类箱子、两类插槽、门、轨道和转向板；设置供电来源和朝向；校验定位、撤销/重做、保存/重开、试玩返回都从实际 UI 走通。用相同任务记录改前/改后的查找和操作步骤，不能只靠截图判断易用性。

依据：[编辑器指南](../Editor/LevelEditorGuide.md)、[LevelEditorWindow.cs](../../Assets/Scripts/Editor/LevelEditor/LevelEditorWindow.cs)。R05 独立补齐目录功能，R02 不凭一次界面整理宣称 E01–E12 全部完成。

### R03 · 场景去文字与门—插槽材质配色

**用户方向：** 删除插头和终点旁常驻的提示文字，用材质颜色区分门与对应插头，减少场景信息堆积。这里“终点”对应计入通关的目标插槽；目标环和插头图形分别表示目标职责与给门供电的职责。

这个方向可行，但现有规则包含一门多来源、一源多门、Any/All，以及“目标同时给门供电”。因此需要先定义配色单位，不能假定每扇门只有一个独占插头。

- **配色候选：** 按门分配连接色，在门框/端口与对应插头上重复；同一插头连多门时显示多个分段色标。也可以沿用来源色、在门上显示多个来源端口，需用实际复杂布局比较后决定。
- **冗余识别建议：** 颜色配合少量形状、纹样或端口图形；不依赖浮动文字承担日常辨认。目标环与插头符号继续可组合，能源箱保持通用外观，避免让人以为箱子也需同色配对。
- **状态分层：** 连接色在断电时仍保留；亮度、填充或状态灯表达电力。Any/All、多来源的当前满足情况，以及“断电但被占据而保开”需要独立图形说明。目标身份在箱子覆盖后仍应从外缘可见。
- **立项前待定：** 调色板、配色单位、图形冗余方案；门旁现有条件文字如何处理；连线是否改为按需显示。插头和目标旁常驻文字的删除是本项方向，其他文字不自动扩大删除范围，也不默认改成另一套常驻小字。
- **验收目标：** 默认游玩画面中上述插头/目标文字消失；720p/1080p、双视角、远近距离、箱子占据和灰阶下能区分目标职责、连接与供电状态；覆盖一源多门、Any/All、多路交接、普通箱占槽、断电保开及撤销/重开；颜色映射在重载与表现重建后稳定。

依据：[现有视觉语义与 v0.2.0 记录](../Art/VisualReadabilityReview.md)、[GDD](../Gameplay/GameDesign.md) 第 4/10 节。R03 将调整当前标牌方案；正式实施时同步当前设计规范，保留 v0.2.0 的历史验收原貌。

### R04 · 第三人称镜头与场景美术综合优化

**目标：** 缓解小地图中的逼仄、遮挡和镜头被挤近的问题，保留第三人称环绕观察与俯视解谜各自的用途。

只读基线：当前 FOV 为 55°、默认跟随距离 3.2 m、俯角 25°、目标高度 0.55 m；墙的镜头碰撞盒高 1.54 m。相机避障会参与最终机位计算。**这些参数说明需要联合检查，尚不能证明哪一项是体验问题的主因。**

- 先在同一关卡、同一路径和窗口尺寸下比较：A 镜头参数调整；B 镜头配合较低墙体/门框；C 镜头配合遮挡墙局部淡出或隐藏。方案数量、具体参数与美术形式在立项时收敛。
- 镜头侧检查俯角、距离、FOV、跟随目标、阻尼、避障层与碰撞体；美术侧检查墙/门顶的体积、前景遮挡及地图外边缘。降低可见墙高时必须同时审查镜头碰撞体，否则画面变矮但避障仍可能把相机推近。
- 墙体视觉和镜头碰撞的改动要保持规则中的不可通行格；隐藏/淡出不改变关卡解法。先保持现有格长、布局和主角尺寸做对比，扩大地图或整体缩放只有在证据支持且明确纳入范围时再讨论。
- 可比较较高俯角的跟随镜头，但默认视角仍按现有第三人称契约；是否改变其定位需后续明确决定。先确认资产需要怎样改变，再决定是否进入 Blender 局部修改。
- **立项前待定：** 希望更贴近角色还是更容易看清棋盘、接受低墙或局部隐藏的程度、可接受的镜头运动与最小观察范围。用户描述的逼仄感作为问题输入，方案效果仍需实机比较。
- **验收目标：** 窄门、贴墙、转角、边界及推箱连续路径录屏；检查镜头穿模、突然拉近/恢复、主体遮挡和可见下一操作格；覆盖 360° 环绕、长按方向锁定、动作中切视角、暂停、撤销/重开及俯视全图。记录实际参数与前后对比，自动测试不能代替体验检查。

依据：[CameraRig.cs](../../Assets/Scripts/Presentation/CameraRig.cs)、[BoardView.cs](../../Assets/Scripts/Presentation/BoardView.cs)、[GDD](../Gameplay/GameDesign.md) 第 3 节。与 R03 共用测试机位；镜头未稳定前，材质可探索，但不提前封版其最终屏幕可读性。

## 建议补充的迭代

### R05 · 关卡目录管理与发布前校验

现有正式目录与运行时选关已实现，编辑器内加入/移出/排序和构建前全量参考解法门禁仍缺失。这是编辑器核心交付链中的缺口，建议优先于更多装饰和新机制。

- **建议范围：** 在编辑器界面管理正式目录，显示结构校验、参考解法及过期状态；构建前检查目录引用和当前内容对应的参考解法。此处“发布”指加入本地正式目录与构建准备，不涉及上传。
- **待定：** 独立面板或嵌入 R02 的目录区、错误呈现、目录变更后的记录方式。
- **验收目标：** 从新图→保存→录制/校验解法→加入目录→排序→游戏内选关走通；移出后保留源关卡；缺失资源、重复 ID、无效/过期解法能阻止不合格构建并定位问题。另存副本必须以新 ID 建立有效证明。

依据：[实现状态](../ImplementationProgress.md)、[GDD](../Gameplay/GameDesign.md) E10 与第 11.4 节；不重复开发现有录制、原子保存和基础校验。

### R06 · 玩家进度与成绩保存

设置已经保存，但正式玩家通关进度与最佳成绩尚未实现。建议先补最小的本地存档闭环。

- **建议范围：** 已完成关卡、最近游玩关卡、最佳步数/推动数及选关展示；首轮“继续”可只返回最近关卡的起点，是否恢复中途局面单独定范围。
- **待定：** 步数与推动数分别记录还是同一次成绩、关卡内容更新后旧成绩如何处理、继续入口语义。现有全关可选的规则保留，解锁门槛需另议。
- **验收目标：** 退出并重新打开独立 Player 后恢复；按稳定关卡 ID 关联，处理移除/改版关卡、损坏存档和首次启动；作者试玩、GM 和现场编辑不污染正式成绩；写入失败可恢复。

### R07 · 新玩家引导与难度节奏复核

原前三关已删除，当前正式目录为 L04–L12；L07/L08 已承担转向教学。建议复核从现有首关开始能否顺利理解规则，**不能仅凭历史关号判定当前首关太难，也不预设必须恢复旧关卡或增加教程关**。

- **建议范围：** 能源箱/普通箱、目标/供电、Any/All、轨道/转向板、撤销和双视角的首次接触；结合 R01 的简短帮助和 R03 的图形语义，检查现有九关的信息与难度递进。
- **待定：** 在现有关卡提供按需提示，还是后续确需独立入门内容；有独立试玩反馈后再决定改图或排序。
- **验收目标：** 明确记录首次玩法理解、误解和卡点；可用性操作记录与独立玩家反馈分开。只有改图/改顺序时才更新对应数据、参考解法与回归；不把自动通关当作人类难度证据。

### R08 · 操作反馈与基础音效

目前已有移动/推动/门动画和状态表现，音效及表情反馈仍有缺口。建议补齐最小集合，让受阻、落位和供电变化更易理解。

- **建议范围：** 推动接触、受阻、落位、通电/断电、完成、UI 点击等基础反馈；是否加入移动音和简短表情气泡在立项时收敛。避免重复放大已有灯光或堆叠长动画。
- **待定：** 素材风格与来源、音量层级、气泡是否纳入首轮；沉浸配乐和大量装饰特效可后置。
- **验收目标：** 音量/静音生效；长按受阻不刷屏或重复轰鸣；撤销、重开、暂停和切关后不播放旧反馈；关闭反馈时仍能读懂稳定状态，规则与计数不变。

### R09 · 编辑器完整流程与独立 Player 交付验收

已有 EditMode/PlayMode、Windows 构建及启动证据，但不等同于完整编辑器用户流程、独立 Player 的交互通关和性能验收。建议单列交付迭代，避免把最后一个功能版本的通过误当作整体完成。

- **建议范围：** 按 GDD 第 11.4 节从 UI 完成完整作者路径；在正式 Player 中实际完成至少两关并验证进度恢复；覆盖全部正式关卡参考解法、菜单/输入/双视角、分辨率和基本性能；检查正式构建的数据范围及开发工具隔离，整理交付说明与已知限制。
- **待定：** 最终交付范围、验收机器与性能目标、试玩路径和证据格式；立项时固定，测量前不宣称达标。
- **验收目标：** 每项要求对应可复现的实际证据；功能测试、界面操作、独立试玩和构建启动分别说明。缺少证据的历史条目须明确复验或继承依据，不凭较新版本通过就自动改写旧状态。
- v0.2.1 当前仍记录为受阻；v0.3.0 已有后续回归。本次只保留这些事实，R09 立项时再核对覆盖关系和是否需补验，不在路线图维护中擅自补记通过。

## 建议顺序与控制范围
